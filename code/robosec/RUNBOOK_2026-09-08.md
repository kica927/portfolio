# RoboSec 실기 실행 순서 — 2026-09-08 (하드웨어 마지막 날)

하드웨어를 쓸 수 있는 마지막 날이다. **미리 확정해 둔 가설을 실기로 확증**하는
것이 목표다 — 그날 처음 생각하지 않는다. in-process 로 이미 20/21 을 확인했고
(`results/inprocess_2026-08-30.md`), 실기에서는 그것이 실제 차량에서도 같은지만
본다.

## 0. 원칙 (먼저 읽을 것)

- **grippers 실기 검증이 항상 우선이다.** RoboSec 은 그 뒤 남는 시간에 한다.
  보안 실험 때문에 캡스톤 데이터 수집을 밀면 안 된다.
- **모든 실험을 녹화 위에서 한다.** 녹화가 안 걸린 실험은 하지 않은 것과 같다
  — 9월 8일 이후엔 재현이 불가능하다.
- **차량을 멈출 때 모터 노드를 죽이지 않는다.** 마지막 명령이 래치된다.
  정지는 `stop=True` 명령으로만.
- **한 번에 한 공격.** 두 개를 겹쳐 관측하면 어느 것이 무엇을 유발했는지 못 가른다.
- 접속·컨테이너·`ROS_DOMAIN_ID=21` 은 grippers HANDOFF.md 규칙 그대로.

> **baseline @ ad619b9 에서도 20/21 재현을 2026-08-30 에 확인**했다. 다만 baseline
> 은 공격자에게 보고를 돌려주지 않는다(host_ip 로만 보고) — a3-replay 의 보고
> 관측에만 영향이 있고 F1·F2 에는 없다.

## 2. Pi IP 확인

Pi 는 iptime 공유기에서 **192.0.2.7 로 고정**되어 있다(2026-08-30 확인). 아래
`PI_IP` 자리에 그대로 쓴다.

    ssh pi@192.0.2.7 'hostname -I'      해당 IP 로 응답하면 준비된 것

혹시 안 잡히면 mDNS 로: `ssh pi@raspberrypi.local 'hostname -I'`.

## 3. 녹화 시작 (별도 터미널, 계속 켜 둠)

**녹화는 RoboSec 이 아니라 pi_capture 가 한다** — RoboSec 엔 녹화 기능이 없다.
pi_capture 의 두 경로 중 하나를 쓴다. 둘 다 `/mission/state` 와 `cmd_vel` 을
남기고, 5단계의 어댑터가 어느 쪽이든 같은 JSONL 로 바꾼다.

    bash /tmp/pi_capture/record.sh "robosec 공격 확증"
    python3 /tmp/pi_capture/tap.py --out /tmp/capture_out/robosec1 --topics /cmd_vel /mission/state --label "robosec 확증"

위는 두 경로다 — bag(전체 토픽) 또는 CSV(가벼움). 하나만 쓴다. `tap.py` 는
`--out` 이 필수다(없으면 에러). CSV 를 쓰면 5단계에서 `csv_to_jsonl`, bag 이면
`bag_to_jsonl` 을 쓴다.

RoboSec 실험은 grippers 정상 미션과 **분리된 전용 세션**에서 한다 — pi_capture 는
구독만 하지만, RoboSec 의 attacker 는 명령을 주입하므로 정상 미션과 겹치면 안 된다.

## 3.5 미션 노드를 UDP 수신 상태로 기동 (컨테이너 안) ⚠️ 핵심

주입을 받으려면 Pi 에서 `mission_orchestrator` 가 **실제 `UdpHostLink`** 로 떠
있어야 한다. 5005 수신 소켓은 `UdpHostLink.__init__` 순간 `0.0.0.0:5005` 로
열린다(baseline `udp_host_link.py:48`, `_rx.bind`). 이는 `use_fake_host:=false` 일 때 생성되며,
**노드·bringup 둘 다 그게 기본값**이다.

> HANDOFF 의 "fake 로 떠 있다"는 2026-08-28 특정 세션의 낡은 상태다. 9월 8일은
> 새로 부팅하므로 "지금 fake 다"를 전제하지 말고, **부팅 시 `use_fake_host` 만
> 확인**한다.

### ⚠️⚠️ 먼저 모터 컨트롤러를 띄운다 — 없으면 바퀴가 안 돈다

`Ros2MecanumBase` 는 `cmd_vel` 에 **publish 만** 한다(`ros2_mecanum_base.py:38`).
그 `cmd_vel` 을 받아 실제로 STM32 에 모터 명령을 쓰는 것은 **odom_publisher
노드**다(`odom_publisher_node.py:134`, `app_cmd_vel_callback`). 이 노드가 없으면:

- 주입한 nan/속도가 `cmd_vel` 로 나가도 **구독자가 0 이라 바닥에 버려진다** — 바퀴가 안 움직인다.
- 그러면 F1 을 "nan 이 바퀴까지 안 갔다(안전)" 로 **틀리게 결론낸다** — 실제로는 구동 체인이 통째로 없었을 뿐이다.
- 게다가 `liveness()` 가 `cmd_vel` 구독자 수로 base 건강을 판정하므로(`ros2_mecanum_base.py:75`), 구독자 0 → orchestrator 가 base 를 죽은 걸로 보고 **구동 자체를 거부**할 수 있다.
- 에러도 안 난다 — base 생성자는 퍼블리셔만 만들고 조용히 돈다.

그래서 **컨트롤러를 orchestrator 보다 먼저** 띄운다(2026-08-28 팀도 `run_ctrl.sh`
를 별도로 먼저 띄웠다). 이 재기동이 STM32 도 재초기화한다.

**②-a 【Pi B1】 모터 컨트롤러 (이 창을 먼저, 켜둔다):**

    export ROS_DOMAIN_ID=21
    export need_compile=False
    export DEPTH_CAMERA_TYPE=ascamera
    export MACHINE_TYPE=MentorPi_Mecanum
    source /opt/ros/humble/setup.zsh
    source /ros2_ws/install/setup.zsh
    source /home/ubuntu/third_party_ros2/third_party_ws/install/setup.zsh
    ros2 launch controller odom_publisher.launch.py

`need_compile` 을 export 안 하면 launch 가 KeyError 로 죽는다
(`odom_publisher.launch.py:11` 이 `os.environ['need_compile']` 을 읽는다).

**②-b 【Pi B2】 그 다음에 orchestrator** (`bringup.launch.py` 를 쓰지 말고 노드
하나만 개별 기동 — 2026-08-28 팀이 실제로 쓴 방식):

    ros2 run grippers_mission mission_orchestrator --ros-args -p use_fake_host:=false -p use_fake_arm:=true -p use_fake_base:=false -p host_ip:=<맥A_IP>

**확인 — 둘을 띄운 뒤 반드시:**

    ros2 topic info /cmd_vel

`Subscription count: 1` 이상이어야 한다. 0 이면 컨트롤러가 안 붙은 것이고,
그 상태로 ④를 쏘면 **무의미하다**(바퀴가 안 도니 F1·F2 를 관측할 수 없다).

세 가지를 반드시 지킨다.

- **`use_fake_arm:=true`.** full bringup 을 때리면 `arm_driver_node` 가 기동
  시 오프셋을 대조해, 다르면 `ArmCalibrationMismatchError`(baseline
  `arm_driver_node.py:236`) 로 **기동을 거부**한다(`verify_calibration` 기본 True 는
  같은 파일 `:258`). 08-29 LeRobot 이
  오프셋을 덮었을 수 있어, 그대로 bringup 하면 하드웨어 마지막 날을 팔 디버깅에
  쓴다. RoboSec 은 팔을 안 쓴다 — 노드 개별 기동이면 `arm_driver_node` 를 애초에
  안 띄우고, 미션 내부 팔도 fake 라 이중으로 피한다.
- **`use_fake_base:=false` (진짜 바퀴).** F1(nan 이 바퀴까지 가나)·F2(IDLE
  로봇이 실제로 움직이나) 는 실제 바퀴 반응을 봐야 성립한다. 기본값이 false 라
  그대로 두면 되지만, 명령에 명시해 실수를 막는다.
- **맥에서 정당한 Host 미션을 동시에 돌리지 않는다.** 수신 소켓이 `0.0.0.0` 이라
  `host_ip` 와 무관하게 받으므로, 진짜 Host 없이도 주입은 먹힌다. `host_ip` 는
  Pi 가 보고(5006)를 보낼 목적지일 뿐이다. attacker 가 5005 의 **유일한 발신자**
  여야 한다 — 정당한 Host 까지 같이 쏘면 두 발신자가 섞여 원인을 못 가린다.

기동 후 5005 가 열렸는지 확인:

    ros2 node list

`/mission_orchestrator` 가 보이면 준비된 것이다.

## 4. 공격 순서

**차량을 받침대에 올려 바퀴를 띄운 채로 한다** — F1·F2 는 "바퀴가 도는가"라
띄워도 그대로 관측되고, 병진·충돌이 없어 급정지가 거의 필요 없다. 메인 전원
스위치는 STM32·Pi 가 배터리를 공유해 내리면 Pi 까지 꺼지므로(세션·녹화 손실,
SD 손상 위험) 상시 E-STOP 으로 쓰지 않고 **최후수단으로 손 닿는 곳에만** 둔다.
각 공격 사이 30초 이상 두고, **다음 공격 전에 알려진 상태로 복귀**한다.

> ⚠️ **순서가 중요하다 — F2(a5)를 F1(a4)보다 먼저 한다.** a4 는 `state=APPROACH`
> 를 주입해 FSM 을 **IDLE→APPROACH 로 전이**시킨다(baseline `BaselineIdleState` 가
> APPROACH 명령에 `return BaselineApproachState()` 로 무조건 전이). 그런데
> a5(F2)는 "**IDLE** 인 로봇에 속도를 주면 바퀴가 도는가"를 보는 것이라, a4 를
> 먼저 하면 a5 가 더 이상 IDLE 을 시험하지 못한다. 그래서 a5 를 앞에 둔다.
> a1·a5 는 FSM 을 IDLE 에 그대로 둔다(a1 은 전부 폐기, a5 는 전이 차단).

| # | 명령 | 확증하려는 것 |
|---|---|---|
| 1 | `python3 attacker.py a1-corruption --target PI_IP --live` | D5 가 실기에서도 손상 패킷을 버리는가 (바퀴 안 움직여야) |
| 2 | **IDLE 확인** → `python3 attacker.py a5-state-mismatch --target PI_IP --live` | IDLE 로봇에 GRASP/속도를 주면 **바퀴가 도는가** (F2 확증) |
| 3 | `python3 attacker.py a4-extreme --target PI_IP --state APPROACH --live` | 극단값이 실제로 0.1 m/s 로 잘리는가. **nan 케이스를 특히 관찰** (F1) |
| 4 | `python3 attacker.py a2-spin-impurity --target PI_IP --live` | 회전+병진 혼합이 거부되고 차가 서는가 (D2) |
| 5 | `python3 attacker.py a3-replay --target PI_IP --count 30 --live` | 재전송이 상태를 흔드는가 (시퀀스 번호 부재의 실제 영향) |

**2번(a5) 직전에 IDLE 을 확인한다** — Pi orchestrator 창(B2)에서:

    ros2 topic echo /mission/state --once

`IDLE` 이 아니면(예: a1 이 예상과 달리 상태를 옮겼거나 이전 세션 잔여), 정상
IDLE 명령을 한 번 보내 복귀시킨 뒤 a5 를 쏜다. IDLE 이 아니면 a5 는 F2 가
아니라 다른 상태를 시험하게 되어 결과 해석이 깨진다.

**F1(nan) 을 볼 때 주의:** 3번 극단값 세트의 **다섯 번째(마지막) 패킷**이 nan
이다(1000 → -1000 → 999 → inf → nan). 그 순간 차량이
- 정지하면 → 드라이버가 어딘가에서 nan 을 0 으로 떨어뜨린 것 (안전)
- 마지막 속도를 유지하면 → nan 이 무시된 것 (은근히 위험 — 명령이 먹히지 않음)
- 예측 불가하게 튀면 → nan 이 STM32 까지 간 것 (위험)
어느 쪽인지 녹화와 눈으로 반드시 기록한다.

목록을 찍어 준다. 그 이름으로 다시 돌린다.

## 6. 하드웨어 종료 이후

실기가 끝나도 RoboSec 은 계속된다:
- in-process probe 는 grippers 코드가 바뀔 때마다 회귀로 돌린다
- 녹화한 bag·JSONL 이 영구 회귀 입력이 된다
- F1·F2 후속(방어 추가 후 재확인)은 전부 in-process 로 가능하다
