## 1. Problem — 무슨 문제를 푸는가

바닥에 흩어진 물건을 로봇이 스스로 찾아 종류별 상자에 정리하고, 요청하면
가져다줍니다.

정리는 로봇 태스크로서 특이한 성질이 하나 있습니다. **목표 상태가 목록으로
주어지지 않습니다.** "A를 B로 옮겨라"는 경로만 풀면 되지만, "정리해라"는 무엇이
몇 개 있는지조차 모르는 상태에서 시작하고, 물체 하나를 옮길 때마다 바닥 상태가
바뀝니다. 그래서 한 번 실행하고 끝나는 대본이 아니라 **관측 → 판단 → 행동이 매
사이클 닫히는 루프 FSM** 이 필요합니다.

## 2. Architecture — 시스템 구성

두 대의 컴퓨터가 UDP 로 붙어 있고, **좌표를 누가 소유하는가**로 역할을 갈랐습니다.

```
                  Host PC (macOS / M1 Pro)
        ┌──────────────────────────────────────┐
        │ 오버헤드 웹캠 2대 · ArUco 포즈 추정   │
        │ geti 물체 검출                        │
        │ 월드 모델 · 경로 계획 · 명령 권한     │
        └───────────────────┬──────────────────┘
                            │  UDP  5005 명령 / 5006 보고
                            │  JSON · 5필드 · 최신 것만 유효
        ┌───────────────────┴──────────────────┐
        │        Raspberry Pi 5 (Ubuntu 24.04)  │
        │  ROS 2 Humble · 미션 FSM (10 Hz)      │
        │  속도 클램프 · 워치독 · 안전 판정     │
        └────────┬──────────────────┬───────────┘
                 │                  │
            메카넘 베이스        SO-ARM101 팔
                 │                  │
          LiDAR(LD19) / IMU      뎁스 카메라
```

**Host 가 좌표를, Pi 가 물리를 소유합니다.** Host 는 물체 위치와 차량 자세를
알고 어디로 갈지 정하고, Pi 는 그 명령을 받아 실제로 바퀴와 관절을 돌리며
"지금 이 명령을 안전하게 수행할 수 있는가"만 판단합니다.

Pi 쪽 미션 FSM:

```
IDLE → APPROACH → GRASP → CARRY → APPROACH_BOX → INSERT → DONE
```

### Ports & Adapters

도메인 로직이 ROS 2 도 서보 SDK 도 모르게 분리했습니다.

| Port | Real Adapter | Fake Adapter |

`IDLE → DONE` 전 구간이 CI 에서 돕니다.

## 4. Design Decisions — 왜 이렇게 정했나

### 속도 한계를 Host 가 아니라 Pi 가 집행한다

Host 가 경로를 소유하지만 **바퀴를 실제로 돌리는 것은 Pi** 입니다. 한계는
그것을 어길 수 있는 쪽이 아니라 **물리적으로 집행할 수 있는 쪽**에 있어야
합니다. Host 버그나 패킷 손상으로 `0.1` 이 `1.0` 으로 오더라도 Pi 가 잘라냅니다.
방향은 Host 것을 그대로 두고 크기만 제한합니다 — Pi 가 명령을 *고르지는*
않습니다.

### UDP 는 큐를 쌓지 않고 마지막 것만 덮어쓴다

이 링크가 실어 나르는 것은 **그 순간의 속도 명령**입니다. 오래된 패킷은
쓸모가 없으므로 재전송을 기다리는 것보다 다음 것을 쓰는 쪽이 항상 낫습니다.

### `None` 은 정지가 아니다

명령이 없을 때 "정지"로 바꿔 돌려주지 않습니다. **링크가 끊긴 것과 Host 가
정지를 지시한 것은 전혀 다른 사건**이기 때문입니다. 앞은 워치독이, 뒤는 정상
경로가 처리합니다. 망가진 패킷을 반쯤 읽어 0으로 채우지도 않습니다 — 그 0은
"정지"가 아니라 "모른다"입니다.

### 바구니 접근만 속도를 따로 낮춘다

Host 가 "멈춰"라고 판단한 순간부터 바퀴가 실제로 서기까지 지연이 쌓입니다.

```
Host 루프 한 바퀴 (8 Hz)   125 ms
UDP + Pi 수신               10 ms
Pi 사이클 (10 Hz)          100 ms
────────────────────────────────
합계                       235 ms
```

0.1 m/s 면 그동안 **23.5 mm** 를 더 갑니다. 그런데 INSERT 허용폭은 **±15 mm**
입니다 — **오버슈트가 창보다 큽니다.** 창 안에 우연히 들어갈 수는 있어도
제어되는 것이 아닙니다. 0.06 m/s 로 낮추면 같은 지연이 14 mm 가 되어 창 안에
들어옵니다. 더 못 낮추는 이유는 **데드밴드가 0.05** 이기 때문입니다 — 그 아래는
아무리 오래 줘도 바퀴가 안 도는데 `/odom_raw` 는 움직였다고 보고합니다.

## 6. Problems & Debugging — 계측으로 잡은 결함 5건

실기 5회 실행 로그와 Pi 로그를 전수 대조해 결함 6건을 확정했습니다. 그중 성격이
다른 4건과, 이후(2026-09-05) IMU 재측정으로 잡은 데드밴드 결함 1건입니다.

### 6-1. Pi 제어 주기가 설계의 1/6 이었다

```
Problem     Pi 가 Host 명령을 놓친다
Symptom     로그 타임스탬프 간격 0.6초 — 제어 주기 1.6 Hz (설계 10 Hz)
Hypothesis  루프 안에 블로킹 대기가 있다
Measurement 사이클별 타임스탬프 로그
Root Cause  base.stop() 이 "E-STOP 경로라 안 기다린다"는 docstring 과 달리
            없는 서비스를 wait_for_service(0.5s) 로 매 사이클 기다렸다
Fix         service_is_ready() (논블로킹) 으로 교체
Verification 같은 워크로드 재실행, 사이클 간격 재측정
Result      0.104초 = 9.6 Hz  (1.6 → 9.6 Hz, 6배)
```

**이 결함의 대가가 실행 2회차입니다.** Host 가
`SEARCH_TARGET → APPROACH_PIECE → GRASP` 를 한두 사이클에 지나가자 Pi 는 IDLE 에
남았고, IDLE 은 GRASP 명령을 받지 않으므로 아무 일도 일어나지 않았습니다.
**명령이 안 온 게 아니라 Pi 가 읽을 차례가 오기 전에 다음 명령으로 덮인 것**입니다.
워치독 3사이클도 0.3초가 아니라 1.8초가 됐습니다.

### 6-2. 좌우 정렬 보정이 원리적으로 불가능한 격자였다

```
Symptom     같은 보정값 "+27mm → servo 1 +5.2도" 가 9회 반복되고 끝남
Measurement 팔 서비스 로그: servo 1  2067 -> 2067 (+5.2도), ok=True
Root Cause  "이미 도착" 허용오차가 120 raw(≈10.5도)인데 보정은 59 raw(5.2도) —
            허용오차 안이라 관절이 이동 대상에서 통째로 빠졌다. 그런데
            서비스는 ok=True 를 냈다
분석        좌우 허용오차 10mm, 물체는 턱 앞 약 214mm → 10mm ≈ 2.7도 ≈ 30 raw.
            분간해야 할 단위가 허용오차 격자의 1/4 이다 — 튜닝이 아니라
            원리적으로 수렴할 수 없는 구성이었다
Fix         허용오차를 관절별로 줄 수 있게 하고 servo 1 만 10 raw 로 조임.
            도달 확인 추가 (예전엔 무조건 ok=True)
```

**"실패했는데 성공이라고 보고하는" 부류라 로그만 봐서는 안 보였습니다.** 반복되는
같은 값이 유일한 단서였습니다.

### 6-3. 느린 서비스가 매번 시간 초과로 "실패"했다

```
Symptom     set_gripper / offset_base_yaw: 응답 없음 (3.0s) — 실패로 처리
관찰        팔은 멀쩡히 움직였다. 그리퍼는 168mm 로 열리고 9.5mm 로 닫혔고
            파지도 성공했다. 실패한 것은 호출자의 대기뿐
Root Cause  서버 계약은 "동작 완료까지 붙들고 있다가 응답"인데 호출자는 3.0초만
            기다렸다. 서버 상한을 보면 애초에 못 맞춘다 —
            GRIPPER_MOTION_TIMEOUT(4.0) + GRASP_SETTLE(1.5) = 최악 5.5초
Fix         대기를 서버 상한에서 거꾸로 잡아 8.0초.
            보정 글라이드 단계 수를 이동 거리에 맞춰 3.0초 → 0.5초로 축소
```

오보가 조용하지 않았던 것이 문제였습니다 — 상위 FSM 이 `GRASP_BLOCKED` 사유로
*"servo 1이 거부했다, 재회전 필요"* 를 보고했는데, servo 1 은 거부한 적이 없습니다.

### 6-4. 상대 회전에 절대 한계를 걸지 않았다

`offset_base_yaw` 는 **현재 위치 기준 상대 회전**인데 한계 검사는 한 번의 요청
크기(±15도)만 봤습니다. 같은 요청이 반복되면 매번 통과하면서 얼마든지 멀리
걸어갑니다. 6-1 을 고쳐 보정이 실제로 먹기 시작하면 바로 터질 결함이라, 한계를
**교시 정면 기준 절대각**으로 바꿨습니다. 실측에서 3회 보정 합이 약 14도였습니다 —
15도 한계에 여유가 거의 없었습니다.

> **한 결함을 고치면 다음 결함이 드러납니다.** 6-1(보정이 안 먹음)을 고치는
> 순간 6-4(보정이 누적됨)가 실제 위험이 됩니다. 고치기 전에 미리 막아 둔 것이
> 이 항목입니다.

### 6-5. "합의된" 회전 속도가 데드밴드 아래였다

```
Problem     ALIGN_YAW 에서 회전 명령을 계속 받는데 차가 제자리에서 안 돈다
Symptom     명령은 Host UDP -> orchestrator -> /cmd_vel -> odom_publisher ->
            set_motor 까지 전부 정상으로 내려감. 그런데 IMU 각속도가 0.002 rad/s
Hypothesis  /odom_raw 는 명령을 그대로 적분해서 "돌았다"고 보고하지만, 실제로
            도는지는 다른 센서로만 알 수 있다
Measurement tools/rotation_threshold_sweep.py 로 명령값별 IMU 실측 스윕
Root Cause  회전에도 데드밴드가 있고, 팀이 합의한 값(0.25)이 그 아래였다
            (명령 0.25 -> 실측 0.035, 안 돎. 0.35부터 돎)
Fix         한계를 0.6 으로 상향 — 실측 최소(0.35)의 1.7배, 팔·Hailo 탑재로 늘어난
            무게 변화에도 여유를 둠
Verification 도메인 테스트 스위트 전체 재실행, 회귀 없음 확인
Result      0.25 -> 0.6. 오버슛은 문제 안 됨 — 0.6 의 실제 회전은 약 20도/s,
            Host 루프 10Hz 라 사이클당 2도인데 DRIVE_YAW_TOLERANCE_DEG 는 5도
```

**이 진단이 오래 걸린 이유를 기록해 둡니다.** `/odom_raw` 로그만 보면 전 구간이
멀쩡합니다 — 명령을 그대로 적분해서 돌려주기 때문입니다. 실제로 도는지는 IMU로만
알 수 있었습니다. 2026-08-24 에도 거의 같은 값(0.355)이 한 번 나왔던 기록이 있었는데
— 테스트 코드 주석에 "0.25는 최저값 0.3보다 낮다"고 이미 적혀 있었지만 상수는
그대로였습니다. **아는 것과 고치는 것 사이에 시차가 있었습니다.**

불일치를 통합 시점이 아니라 커밋 시점에 잡습니다.

## 9. Limitations — 정직하게

> ⏱ **하드웨어 접근은 2026-09-08 에 종료됩니다.** 아래 🔴 항목 중 그때까지
> 해결하지 못한 것은 **영구적인 한계로 남습니다.**

- ✅ **(해소) Host ↔ Pi 실기 통합** — 이 문서 초판 시점엔 한 번도 안 붙여 봤다고
  적었으나, `HostCommand`가 이미 확정 5필드(`state`/`linear_x`/`linear_y`/
  `angular_z`/`stop`) 규격으로 구현돼 있었고, 그 뒤 실기 커밋 로그(09-02, 09-04
  밤 등)에 Host 명령으로 로봇이 실제로 움직인 사건이 다수 기록됐습니다. 초판의
  "🔴 한 번도 안 붙어봄"은 8/28 시점 스냅샷이 갱신 안 된 채 남아 있던 것이었습니다.
- 🔴 **사선 진입 INSERT — 방식 자체를 다시 짰지만 전 구간 미검증** — 애초의
  Pi 쪽 LiDAR 기반 좌우 허용치(`BASKET_LATERAL_TOLERANCE_M`, 계산값)는 폐기하고,
  Host 쪽에서 목표영역을 120도 부채꼴로 나눠 어느 방향에서 접근해도 정렬각을
  계산하는 방식으로 바꿨습니다(LiDAR 없이 완결). 코드 자체에 "이 각도 끝까지
  실제 INSERT를 검증하지 않았다"는 경고가 남아 있어, 설계는 바뀌었지만 검증까지
  끝난 것은 아닙니다.
- 🔴 **`identify_target` 지연 미측정** — 클래스를 하나씩 물어보는 방식이라 왕복
  6회의 실제 지연을 아직 재지 않았습니다.
- 🟡 **모터 워치독은 추가했지만 타이밍 값이 추측치** — STM32 쪽에 write_timeout·
  워치독을 추가했지만(2026-09-05), 그 두 값(0.2초·0.5초) 자체가 아직 실기로
  잰 값이 아니라 추측값입니다. 실측 후 조정이 남아 있습니다.
- **end-to-end VLA 가 아닙니다.** Vision-Language-Action 을 모듈로 분해한
  파이프라인이고, 모듈 간 전달은 학습된 특징 벡터가 아니라 심볼(`toy`, `BLUE`)입니다.
  5주 안에 정책 학습 데이터를 모을 수 없었고, 모듈형이 부분 검증과 병목 측정에
  유리해 **의도적으로** 분해했습니다.
- macOS Host 에서는 **초점을 고정할 수 없습니다** — AVFoundation 백엔드가
  `CAP_PROP_FOCUS` 를 지원하지 않아 ArUco 위치 정확도가 Windows 만큼 안 나올 수
  있습니다.

## 10. Future Work

이 시스템은 **보안 연구의 testbed** 로 이어집니다.

Host↔Pi 링크를 만들면서 확인한 것: `UdpHostLink` 는 `0.0.0.0:5005` 에 바인드하고,
수신 루프가 **송신자 주소를 버립니다.** 인증도, 시퀀스 번호도, 타임스탬프도
없습니다. 같은 망 안의 누구든 속도 명령을 보낼 수 있고, 마지막 것이 이깁니다.

이것은 이 프로젝트의 결함이라기보다 **연구 질문**입니다:

> 조작된 Host 명령이 ROS 2 기반 로봇 시스템에서 안전하지 않은 상태 전이를
> 일으킬 수 있는가?

Pi 쪽에는 이미 방어층이 여럿 있습니다 — 속도 클램프, 워치독, 상태별 명령 수용
제한, 망가진 패킷 폐기. **그 방어층이 실제로 어디까지 버티는지 측정하는 것**이
다음 프로젝트 `robosec` 입니다.

→ [`plans/robosec/threat_model.md`](../plans/robosec/threat_model.md)
