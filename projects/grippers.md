## 1. Problem — 무슨 문제를 푸는가

바닥에 흩어진 물건을 로봇이 스스로 찾아 종류별 상자에 정리하고, 요청하면
가져다줍니다.

정리는 로봇 태스크로서 특이한 성질이 하나 있습니다. **목표 상태가 목록으로
주어지지 않습니다.** "A를 B로 옮겨라"는 경로만 풀면 되지만, "정리해라"는 무엇이
몇 개 있는지조차 모르는 상태에서 시작하고, 물체 하나를 옮길 때마다 바닥 상태가
바뀝니다. 그래서 한 번 실행하고 끝나는 대본이 아니라 **관측 → 판단 → 행동이 매
사이클 닫히는 루프 FSM** 이 필요합니다.

## 2. Architecture — 시스템 구성

두 대의 컴퓨터가 UDP 로 붙어 있고, **좌표를 누가 소유하는가**로 역할을 갈랐습니다.

```
                  Host PC (macOS / M1 Pro)
        ┌──────────────────────────────────────┐
        │ 오버헤드 웹캠 2대 · ArUco 포즈 추정   │
        │ geti 물체 검출                        │
        │ 월드 모델 · 경로 계획 · 명령 권한     │
        └───────────────────┬──────────────────┘
                            │  UDP  5005 명령 / 5006 보고
                            │  JSON · 5필드 · 최신 것만 유효
        ┌───────────────────┴──────────────────┐
        │        Raspberry Pi 5 (Ubuntu 24.04)  │
        │  ROS 2 Humble · 미션 FSM (10 Hz)      │
        │  속도 클램프 · 워치독 · 안전 판정     │
        └────────┬──────────────────┬───────────┘
                 │                  │
            메카넘 베이스        SO-ARM101 팔
                 │                  │
          LiDAR(LD19) / IMU      뎁스 카메라
```

**Host 가 좌표를, Pi 가 물리를 소유합니다.** Host 는 물체 위치와 차량 자세를
알고 어디로 갈지 정하고, Pi 는 그 명령을 받아 실제로 바퀴와 관절을 돌리며
"지금 이 명령을 안전하게 수행할 수 있는가"만 판단합니다.

Pi 쪽 미션 FSM:

```
IDLE → APPROACH → GRASP → CARRY → APPROACH_BOX → INSERT → DONE
```

## 4. Design Decisions — 왜 이렇게 정했나

### 속도 한계를 Host 가 아니라 Pi 가 집행한다

Host 가 경로를 소유하지만 **바퀴를 실제로 돌리는 것은 Pi** 입니다. 한계는
그것을 어길 수 있는 쪽이 아니라 **물리적으로 집행할 수 있는 쪽**에 있어야
합니다. Host 버그나 패킷 손상으로 `0.1` 이 `1.0` 으로 오더라도 Pi 가 잘라냅니다.
방향은 Host 것을 그대로 두고 크기만 제한합니다 — Pi 가 명령을 *고르지는*
않습니다.

### UDP 는 큐를 쌓지 않고 마지막 것만 덮어쓴다

이 링크가 실어 나르는 것은 **그 순간의 속도 명령**입니다. 오래된 패킷은
쓸모가 없으므로 재전송을 기다리는 것보다 다음 것을 쓰는 쪽이 항상 낫습니다.

### `None` 은 정지가 아니다

명령이 없을 때 "정지"로 바꿔 돌려주지 않습니다. **링크가 끊긴 것과 Host 가
정지를 지시한 것은 전혀 다른 사건**이기 때문입니다. 앞은 워치독이, 뒤는 정상
경로가 처리합니다. 망가진 패킷을 반쯤 읽어 0으로 채우지도 않습니다 — 그 0은
"정지"가 아니라 "모른다"입니다.

### 바구니 접근만 속도를 따로 낮춘다

Host 가 "멈춰"라고 판단한 순간부터 바퀴가 실제로 서기까지 지연이 쌓입니다.

```
Host 루프 한 바퀴 (8 Hz)   125 ms
UDP + Pi 수신               10 ms
Pi 사이클 (10 Hz)          100 ms
────────────────────────────────
합계                       235 ms
```

0.1 m/s 면 그동안 **23.5 mm** 를 더 갑니다. 그런데 INSERT 허용폭은 **±15 mm**
입니다 — **오버슈트가 창보다 큽니다.** 창 안에 우연히 들어갈 수는 있어도
제어되는 것이 아닙니다. 0.06 m/s 로 낮추면 같은 지연이 14 mm 가 되어 창 안에
들어옵니다. 더 못 낮추는 이유는 **데드밴드가 0.05** 이기 때문입니다 — 그 아래는
아무리 오래 줘도 바퀴가 안 도는데 `/odom_raw` 는 움직였다고 보고합니다.

## 6. Problems & Debugging — 계측으로 잡은 결함 6건

실기 로그와 Pi 로그를 전수 대조해 결함 8건을 확정했습니다. 성격이 다른 4건,
(2026-09-05) IMU 재측정으로 잡은 데드밴드 결함 1건, (2026-09-05) 파지 판정이
AND↔OR 로 여러 번 뒤집힌 진짜 원인 1건, (2026-09-07) 두 번의 회전정지 사고로
드러난 하드웨어 플랫폼 자체의 구조적 한계 1건, 그리고 (2026-09-08, 하드웨어
접근 마지막 날) 재기동 시 모터가 완전 무응답이던 사고의 근본원인 1건입니다.

### 6-1. Pi 제어 주기가 설계의 1/6 이었다

```
Problem     Pi 가 Host 명령을 놓친다
Symptom     로그 타임스탬프 간격 0.6초 — 제어 주기 1.6 Hz (설계 10 Hz)
Hypothesis  루프 안에 블로킹 대기가 있다
Measurement 사이클별 타임스탬프 로그
Root Cause  base.stop() 이 "E-STOP 경로라 안 기다린다"는 docstring 과 달리
            없는 서비스를 wait_for_service(0.5s) 로 매 사이클 기다렸다
Fix         service_is_ready() (논블로킹) 으로 교체
Verification 같은 워크로드 재실행, 사이클 간격 재측정
Result      0.104초 = 9.6 Hz  (1.6 → 9.6 Hz, 6배)
```

**이 결함의 대가가 실행 2회차입니다.** Host 가
`SEARCH_TARGET → APPROACH_PIECE → GRASP` 를 한두 사이클에 지나가자 Pi 는 IDLE 에
남았고, IDLE 은 GRASP 명령을 받지 않으므로 아무 일도 일어나지 않았습니다.
**명령이 안 온 게 아니라 Pi 가 읽을 차례가 오기 전에 다음 명령으로 덮인 것**입니다.
워치독 3사이클도 0.3초가 아니라 1.8초가 됐습니다.

### 6-2. 좌우 정렬 보정이 원리적으로 불가능한 격자였다

```
Symptom     같은 보정값 "+27mm → servo 1 +5.2도" 가 9회 반복되고 끝남
Measurement 팔 서비스 로그: servo 1  2067 -> 2067 (+5.2도), ok=True
Root Cause  "이미 도착" 허용오차가 120 raw(≈10.5도)인데 보정은 59 raw(5.2도) —
            허용오차 안이라 관절이 이동 대상에서 통째로 빠졌다. 그런데
            서비스는 ok=True 를 냈다
분석        좌우 허용오차 10mm, 물체는 턱 앞 약 214mm → 10mm ≈ 2.7도 ≈ 30 raw.
            분간해야 할 단위가 허용오차 격자의 1/4 이다 — 튜닝이 아니라
            원리적으로 수렴할 수 없는 구성이었다
Fix         허용오차를 관절별로 줄 수 있게 하고 servo 1 만 10 raw 로 조임.
            도달 확인 추가 (예전엔 무조건 ok=True)
```

**"실패했는데 성공이라고 보고하는" 부류라 로그만 봐서는 안 보였습니다.** 반복되는
같은 값이 유일한 단서였습니다.

### 6-3. 느린 서비스가 매번 시간 초과로 "실패"했다

```
Symptom     set_gripper / offset_base_yaw: 응답 없음 (3.0s) — 실패로 처리
관찰        팔은 멀쩡히 움직였다. 그리퍼는 168mm 로 열리고 9.5mm 로 닫혔고
            파지도 성공했다. 실패한 것은 호출자의 대기뿐
Root Cause  서버 계약은 "동작 완료까지 붙들고 있다가 응답"인데 호출자는 3.0초만
            기다렸다. 서버 상한을 보면 애초에 못 맞춘다 —
            GRIPPER_MOTION_TIMEOUT(4.0) + GRASP_SETTLE(1.5) = 최악 5.5초
Fix         대기를 서버 상한에서 거꾸로 잡아 8.0초.
            보정 글라이드 단계 수를 이동 거리에 맞춰 3.0초 → 0.5초로 축소
```

오보가 조용하지 않았던 것이 문제였습니다 — 상위 FSM 이 `GRASP_BLOCKED` 사유로
*"servo 1이 거부했다, 재회전 필요"* 를 보고했는데, servo 1 은 거부한 적이 없습니다.

### 6-4. 상대 회전에 절대 한계를 걸지 않았다

`offset_base_yaw` 는 **현재 위치 기준 상대 회전**인데 한계 검사는 한 번의 요청
크기(±15도)만 봤습니다. 같은 요청이 반복되면 매번 통과하면서 얼마든지 멀리
걸어갑니다. 6-1 을 고쳐 보정이 실제로 먹기 시작하면 바로 터질 결함이라, 한계를
**교시 정면 기준 절대각**으로 바꿨습니다. 실측에서 3회 보정 합이 약 14도였습니다 —
15도 한계에 여유가 거의 없었습니다.

> **한 결함을 고치면 다음 결함이 드러납니다.** 6-1(보정이 안 먹음)을 고치는
> 순간 6-4(보정이 누적됨)가 실제 위험이 됩니다. 고치기 전에 미리 막아 둔 것이
> 이 항목입니다.

### 6-5. "합의된" 회전 속도가 데드밴드 아래였다

```
Problem     ALIGN_YAW 에서 회전 명령을 계속 받는데 차가 제자리에서 안 돈다
Symptom     명령은 Host UDP -> orchestrator -> /cmd_vel -> odom_publisher ->
            set_motor 까지 전부 정상으로 내려감. 그런데 IMU 각속도가 0.002 rad/s
Hypothesis  /odom_raw 는 명령을 그대로 적분해서 "돌았다"고 보고하지만, 실제로
            도는지는 다른 센서로만 알 수 있다
Measurement tools/rotation_threshold_sweep.py 로 명령값별 IMU 실측 스윕
Root Cause  회전에도 데드밴드가 있고, 팀이 합의한 값(0.25)이 그 아래였다
            (명령 0.25 -> 실측 0.035, 안 돎. 0.35부터 돎)
Fix         한계를 0.6 으로 상향 — 실측 최소(0.35)의 1.7배, 팔·Hailo 탑재로 늘어난
            무게 변화에도 여유를 둠
Verification 도메인 테스트 스위트 전체 재실행, 회귀 없음 확인
Result      0.25 -> 0.6. 오버슛은 문제 안 됨 — 0.6 의 실제 회전은 약 20도/s,
            Host 루프 10Hz 라 사이클당 2도인데 DRIVE_YAW_TOLERANCE_DEG 는 5도
```

**이 진단이 오래 걸린 이유를 기록해 둡니다.** `/odom_raw` 로그만 보면 전 구간이
멀쩡합니다 — 명령을 그대로 적분해서 돌려주기 때문입니다. 실제로 도는지는 IMU로만
알 수 있었습니다. 2026-08-24 에도 거의 같은 값(0.355)이 한 번 나왔던 기록이 있었는데
— 테스트 코드 주석에 "0.25는 최저값 0.3보다 낮다"고 이미 적혀 있었지만 상수는
그대로였습니다. **아는 것과 고치는 것 사이에 시차가 있었습니다.**

### 6-6. 정지 명령이 몇 분째 성공하는데 바퀴는 계속 돌았다 (2026-09-07)

```
Problem     정지 명령을 재전송해도 차량이 멈추지 않는 사고가 하루에 두 번
Symptom     mission_orchestrator의 stop 재전송과 STM32 모터 워치독 둘 다
            몇 분 내내 예외 없이 "성공"을 반복했는데 바퀴는 실제로 안 멈췄다
Measurement bringup.log 전수 조회 — base.stop() 호출 100ms 간격으로 반복
            성공, watchdog도 0.5초마다 반복 성공, 전 구간 buf_write 실패·
            재연결 로그 전혀 없음
Root Cause  이 SDK엔 STM32로부터 모터 회전 자체를 되읽어오는 프로토콜이
            아예 없다 — buf_write()는 쓰기 전용이고, 패킷 파서 맵에
            엔코더/속도 리포트 타입이 없다. "명령을 보냈다"까지만
            확인하고 "로봇이 실제로 그대로 됐다"는 어디서도 검증하지
            않는 완전 개루프 구조였다
Fix         근본 해결 불가능(하드웨어 프로토콜 한계). 이미 오던 IMU
            자이로를 엿보기 캐시로 저장해 모터 워치독에 결합 — 0속도
            재전송 뒤에도 자이로 z축이 여전히 크면 경보. 회전만 잡고
            선속도는 못 잡는다(가속도계 적분 드리프트가 커서 못 믿음).
            Host 쪽은 종료 시 stop 뒤 카메라로 2초 더 관찰해 ArUco
            위치가 실제로 안 바뀌는지 확인하는 절차를 추가
Verification 하드웨어 없이: rotation_stall_detected 순수 함수 5케이스 +
            통합 시험. 실기: 두 사고 모두 재현 조건을 못 좁혀 근본
            원인이 이 개루프 때문인지는 확정하지 못함
Result      부분 완화만 가능. 이 플랫폼은 구조적으로 "명령이 실제로
            실행됐는가"를 소프트웨어만으로 확인할 수 없다
```

**이 결함은 고칠 수 있는 버그가 아니라 하드웨어 플랫폼의 한계로 판명났습니다.**
STM32 펌웨어가 인코더/속도 피드백 패킷 자체를 정의하지 않아서, 이 SDK가
아무리 정교해져도 폐루프 확인은 원천적으로 불가능합니다. IMU 자이로 결합은
회전 정지에 대한 부분적 보완일 뿐, "명령을 보냈다 = 로봇이 그대로 했다"는
가정이 이 시스템 전반에 깔려 있었다는 사실을 이 사고로 처음 확인했습니다.

### 6-7. 부하 판정이 AND→OR→AND 로 여러 번 뒤집힌 진짜 원인 (2026-09-05)

```
Problem     GRASP 최종 성공 판정(부하+뎁스)이 8/26 확정 이후에도 8/29·9/1·
            9/2·9/3·9/5 반복적으로 오탐의 근원이 됐다 — AND 로 하면 정상
            파지를 놓치고, OR 로 풀면 반대 방향(빈손인데 성공 처리) 오탐이
            난다
Hypothesis  AND 와 OR 중 어느 쪽이 맞는 조합인지의 문제라고 오래 생각했다
Measurement 9/3 조사에서 `arm_driver_node._read_load()`가 서보 읽기 *실패*
            시 무엇을 반환하는지 코드를 직접 추적
Root Cause  선택의 문제가 아니었다 — 읽기 실패 시 반환값이 0.0("안전값")
            이었고, 0.0 은 "진짜 빈손"의 정상 관측값과 구분되지 않았다.
            AND/OR 어느 쪽을 골라도 이 값 하나가 두 가지 서로 다른 사건을
            같은 신호로 흘려보내고 있었다
Fix         반환값을 정규화 비율이 절대 나올 수 없는 -1.0 센티널로 바꿔
            "못 읽었다"와 "빈손이다"를 신호 차원에서 분리. 판정은 AND 로
            최종 복귀하되, 부하를 아예 못 읽은 경우만 뎁스 신호 단독으로
            판단하도록 분기. INSERT 쪽 미끄러짐·놓기 판정도 같은 계열
            (옛 0.0 을 직전 표본과 그대로 빼서 오판)이라 함께 가드 처리
Verification 도메인 테스트 스위트 재실행, 회귀 없음 확인
```

**"원인을 안다"와 "고쳤다" 사이에 이틀이 걸렸습니다.** 0.0 이 범인이라는
의심은 9/3 에 이미 섰지만, 실제로 값을 구분 가능한 신호로 바꾼 것은 9/5 였고
그 사이에도 AND/OR 를 오갔습니다. 몇 주에 걸쳐 반복된 증상의 진짜 원인이
"판정 로직"이 아니라 "실패를 성공과 같은 값으로 표현하는 하위 계층"이었다는
점이 6-2(도달 허용오차 격자)·6-3(거짓 실패 보고)과 같은 계열의 교훈입니다.

### 6-8. 재기동해도 모터가 안 움직인다 — 좀비 프로세스가 시리얼 포트를 쥐고 있었다 (2026-09-08)

```
Problem     "차가 완전히 멈췄다"는 신고. IMU 는 정상 수신되는데 모터만 무반응
Symptom     정지·재기동 스크립트 모두 예외 없이 "성공"을 반복해서 찍었다
Hypothesis  6-6 과 같은 구조적 한계(피드백 프로토콜 부재)의 재발일 가능성
Measurement stop_bringup.sh 가 SIGKILL 까지 보내는 것을 확인 후 프로세스
            트리를 직접 추적
Root Cause  launch 관리자(`ros2` 프로세스) 자체가 이미 defunct(좀비)로
            죽어 있었고, 그 아래 더 오래된 `ros_robot_controller` 좀비가
            시리얼 포트를 반쯤 쥔 채 남아 있었다(읽기는 되는데 쓰기만
            막히는 증상과 일치). 좀비는 부모가 없어 kill 로 지워지지
            않는다 — 컨테이너 PID 1 이 orphan 을 reap 하지 않는 것이
            근본 원인으로 추정된다(Docker `--init` 부재로 추정)
Fix         `docker restart`로 컨테이너 자체를 재시작해 좀비를 정리.
            "정지 응답이 왔는데도 안 멈춘 것 같다"는 진단 → 재기동 표준
            절차(IMU/좀비 확인 → 필요시 컨테이너 재시작 → 캘리브레이션
            재확인 → bringup)로 정리해 재현 시 대응 시간을 줄임
Verification 이후 반복 세션에서 재현되지 않음(실기 확인). 컨테이너 PID 1
            자체를 고치는 근본 수정은 하드웨어 접근 종료로 못 함
```

**"성공"이라고 몇 분째 찍히는 로그는 증거가 아니라는 것을 다시 확인한
사고입니다.** 6-2("성공"인데 관절이 안 움직임)·6-3(거짓 실패 보고)의
반대 방향 버전 — 이번엔 거짓 *성공* 보고였고, 원인은 애플리케이션 코드가
아니라 컨테이너 프로세스 관리 계층에 있었습니다.

## 9. Limitations — 정직하게

> ⏱ **하드웨어 접근은 2026-09-08 에 종료됐습니다.** 아래 🔴 항목은 그때까지
> 해결하지 못한 것이라 **영구적인 한계로 남았습니다** — 재검증할 하드웨어가
> 더 없습니다.

- ✅ **(해소) Host ↔ Pi 실기 통합** — 이 문서 초판 시점엔 한 번도 안 붙여 봤다고
  적었으나, `HostCommand`가 이미 확정 5필드(`state`/`linear_x`/`linear_y`/
  `angular_z`/`stop`) 규격으로 구현돼 있었고, 그 뒤 실기 커밋 로그(09-02, 09-04
  밤 등)에 Host 명령으로 로봇이 실제로 움직인 사건이 다수 기록됐습니다. 초판의
  "🔴 한 번도 안 붙어봄"은 8/28 시점 스냅샷이 갱신 안 된 채 남아 있던 것이었습니다.
- ✅ **(해소) 사선 진입 INSERT** — 애초의 Pi 쪽 LiDAR 기반 좌우 허용치는
  폐기하고, Host 쪽에서 목표영역을 부채꼴로 나눠 어느 방향에서 접근해도
  정렬각을 계산하는 방식으로 재설계했습니다(LiDAR 없이 완결). 2026-09-06 밤
  실기(00:00~00:22)로 다중 기물 운반 성공을 확인했고, 2026-09-08 에는 접근
  부채꼴 밖에서 다가올 때 목표가 상자 쪽으로 계속 당겨지던 원인까지 찾아
  `approach_nav_target()`(방위각을 부채꼴 안으로 클램프)로 근본 수정,
  진입각이 매번 달랐던 8개 기물 완주로 재확인했습니다. LiDAR 자체는 이 과정
  중 하드웨어 노드를 아예 안 띄우는 쪽으로 비활성화됐습니다.
- 🔴 **`identify_target` 지연 미측정** — 클래스를 하나씩 물어보는 방식이라 왕복
  6회의 실제 지연을 아직 재지 않았습니다. (2026-09-07 현재도 여전히 미측정.)
- ✅ **(해소) `T_stop`(정지 지연·오버슈트) 실측** — 2026-09-07 오전, 전용 도구
  `t_stop_probe.py`로 실측했습니다. 정지 이벤트 35건, T_stop 중앙값 104.4ms
  (평균 106.9ms, 범위 100~201.5ms), 오버슈트는 사실상 0mm(허용창 ±15mm 안).
  다만 계획했던 "0.1m/s·0.06m/s 각 5회"에는 못 미칩니다 — 직전 명령 속도로
  나눠 보면 계획된 두 값(0.1·0.06)은 8건뿐이고 나머지 27건은 녹화 창에 같이
  잡힌 다른 속도(0.14·0.2 m/s)입니다. 다행히 모든 속도 구간에서 T_stop이
  100~110ms로 일관돼(이 지표 자체가 속도가 아니라 정지 명령까지의 소프트웨어
  왕복 지연을 재는 것이라 당연한 결과), 결론 자체는 바뀌지 않습니다.
- 🔴 **STM32에 모터 회전 피드백 프로토콜 자체가 없다 — 구조적 한계** — 2026-09-07
  실기에서 정지 명령이 몇 분째 "성공"으로 로그되는데 바퀴가 실제로 안 멈추는
  사고가 두 번 났습니다. 원인은 이 SDK가 STM32로부터 엔코더/속도를 되읽어오는
  경로 자체를 갖고 있지 않다는 것 — "명령을 보냈다"까지만 확인할 수 있고
  "로봇이 그대로 했다"는 소프트웨어만으로는 원천적으로 검증 불가능합니다.
  IMU 자이로를 엿보기 캐시로 결합해 회전정지만 부분적으로 감지하도록
  보완했지만(6-6 참고), 근본 해결은 이 하드웨어 세대로는 불가능합니다.
- 🟡 **모터 워치독은 추가했지만 타이밍 값이 추측치** — STM32 쪽(2026-09-05)과
  SO-ARM101 그리퍼/팔 쪽(2026-09-06~07) 둘 다 write_timeout·워치독을
  추가했지만, 타이밍 값들(0.2초·0.5초 등) 자체가 아직 실기로 잰 값이 아니라
  추측값입니다. 실측 후 조정이 여러 세션째 남아 있습니다.
- ✅ **(해소) 바구니 충돌** — 초판의 세 겹 여유거리 땜빵은 근본 원인(고정
  접근 목적지가 차체 회전을 안 봄)을 남겨 뒀었는데, 2026-09-08 실기 사고
  2건(queen, knight)을 분석해 원인을 정확히 찾았습니다 — 접근 부채꼴 밖에서
  다가올 때도 목표가 항상 상자 중심으로 당겨지고 있었습니다. 방위각 클램프
  + 위험 반경 안에서 정렬 무시 강제전진(ESCAPE) 금지, 이 두 가지를 한
  커밋으로 넣어 8개 기물 완주·구동계 경보 0건으로 실기 확인했습니다. 다만
  클램프가 실제로 경로를 꺾는 장면 자체를 목격하지는 못해 결과로만
  검증됩니다.
- 🔴 **컨테이너 안 좀비(defunct) 프로세스 누적 — 근본원인 미해결** — 재기동
  후에도 모터가 완전 무응답이던 사고(§6-8)의 원인이 launch 관리자와
  `ros_robot_controller`가 좀비로 죽어 시리얼 포트를 반쯤 쥐고 있던 것으로
  확정됐습니다. `docker restart`로 매번 정리는 되지만, 컨테이너 PID 1 이
  orphan 을 reap 하지 않는 근본 원인(Docker `--init` 부재로 추정)은
  하드웨어 접근 종료까지 고치지 못했습니다 — 다음에 하드웨어를 다시 쓸 수
  있게 되면 가장 먼저 볼 항목입니다.
- **end-to-end VLA 가 아닙니다.** Vision-Language-Action 을 모듈로 분해한
  파이프라인이고, 모듈 간 전달은 학습된 특징 벡터가 아니라 심볼(`toy`, `BLUE`)입니다.
  5주 안에 정책 학습 데이터를 모을 수 없었고, 모듈형이 부분 검증과 병목 측정에
  유리해 **의도적으로** 분해했습니다.
- macOS Host 에서는 **초점을 고정할 수 없습니다** — AVFoundation 백엔드가
  `CAP_PROP_FOCUS` 를 지원하지 않아 ArUco 위치 정확도가 Windows 만큼 안 나올 수
  있습니다.

## 10. Future Work

이 시스템은 **보안 연구의 testbed** 로 이어졌고, 하드웨어 접근이 끝나기 전
(2026-09-07)에 이미 실기 결과가 나와 있습니다 — 더 이상 "예정"이 아닙니다.

Host↔Pi 링크를 만들면서 확인한 것: `UdpHostLink` 는 `0.0.0.0:5005` 에 바인드하고,
수신 루프가 **송신자 주소를 버립니다.** 인증도, 시퀀스 번호도, 타임스탬프도
없습니다. 같은 망 안의 누구든 속도 명령을 보낼 수 있고, 마지막 것이 이깁니다.

이것은 이 프로젝트의 결함이라기보다 **연구 질문**이었습니다:

> 조작된 Host 명령이 ROS 2 기반 로봇 시스템에서 안전하지 않은 상태 전이를
> 일으킬 수 있는가?

Pi 쪽에는 방어층이 여럿 있습니다 — 속도 클램프, 워치독, 상태별 명령 수용
제한, 망가진 패킷 폐기. `robosec` 프로젝트가 **그 방어층이 실제로 어디까지
버티는지** 하드웨어 없이(in-process, 20/21 확증) 먼저 측정하고, 2026-09-07
실기로 재확증했습니다:

- **재현된 것**: IDLE 상태에서 속도를 주입하면 실제로 바퀴가 돈다(F2),
  시퀀스 번호가 없어 재전송이 상태를 흔든다(a3-replay, 재전송 30건 중
  실질 16건이 모터에 반영됨), 손상 패킷은 실기에서도 전부 폐기된다(A1).
- **모델과 실물이 갈린 지점**: NaN 속도 클램프(F1)를 실기로 확증하려던
  시도가, 그 상태(APPROACH)에서는 raw 명령 자체가 모터로 전달되지 않아
  클램프 경로 자체를 보지 못한 채 끝났습니다 — 안전한 결과지만, 예측했던
  이유(클램프가 막았다)가 아니라 다른 경로(원시 명령을 아예 안 씀)로
  우연히 안전했을 가능성이 있습니다. **F1의 진짜 실물 회귀 확인(IDLE
  상태에서 NaN 단독 주입)은 아직 못 했습니다** — 하드웨어가 남아 있다면
  최우선으로 볼 항목입니다.

→ [`plans/robosec/threat_model.md`](../plans/robosec/threat_model.md)
→ [`code/robosec/results/onhardware_2026-09-07.md`](../code/robosec/results/onhardware_2026-09-07.md)

**하드웨어 접근은 2026-09-08 에 완전히 끝났습니다.** 마지막 세션에서 좀비
프로세스를 모터 무응답 사고의 근본원인으로 확정하고, 바구니 진입각 안전판을
실기로 검증한 뒤 Pi 를 안전 종료했습니다. 이후의 모든 후속 작업(RoboSec 포함)은
**녹화된 ros2 bag, 이미 실측된 상수, 순수 Python 도메인 코드**만으로 진행해야
합니다 — 이 시스템을 Ports & Adapters 로 분리해 둔 것이 여기서도 이어집니다.
하드웨어로만 확인할 수 있었던 항목(§9 의 🔴 표시)은 검증하지 못한 채로 정직하게
남겨 뒀습니다.
