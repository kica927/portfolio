# 임베디드 시리얼 벤치 — Arduino 실기 3종 (보안 · E-STOP 지연 · 링크 특성화)

> *2026 · 단독 · 실기 벤치*
>
> 로봇 작업에서 나온 세 갈래(보안·안전지연·통신)를 **실제 Arduino Uno(ATmega328)
> 위에서 물리적으로 끝단까지** 확인·정량화한 세 개의 작은 벤치다. Arduino 는
> grippers 로봇 하드웨어가 아니라 별개 보드라 **마감(2026-09-08)과 무관**하고,
> 전부 실기 실측값이다.

---

## 왜 세 개를 한 문서로 묶나

셋은 각각 이미 있는 프로젝트의 **끝단을 물리 계층에서 닫거나 정량화**한다 —
따로 크게 부풀리기보다, 한 보드로 얻은 세 실측을 정직한 크기로 함께 둔다.

| | 벤치 | 잇는 곳 | 한 줄 |
|---|---|---|---|
| A | 시리얼 링크 하드닝 + 퍼징 | [udp-network-lab](udp-network-lab.md) · [RoboSec](robosec.md) | 프레이밍을 실제 MCU C 로 포팅, 손상·재전송 거부를 물리 시리얼에서 재현 |
| B | E-STOP 반응지연 | [RoboSec](robosec.md) · [컵 정렬](cup-sorting.md) | 긴급정지 사슬의 **가장 빠른 끝**(입력→ISR)을 실측 |
| C | USB-시리얼 링크 특성화 | [robot-link-timing](#) · [5G/UDP](5g-udp-prototype.md) | RTT·처리량을 payload·baud 두 축으로 스윕, 병목을 숫자로 가름 |

공통 도구: `arduino-cli`(빌드·플래시) + `pyserial` 호스트 프로브. 맥 ↔ Uno(CH340).

## A — 시리얼 링크 하드닝 + 퍼징 〔보안〕

**무엇** — [udp-network-lab](udp-network-lab.md) 의 프레이밍(무결성 CRC32 + 재전송
시퀀스)을 실제 ATmega328 에 C 로 포팅했다. 프레임 `'S''F' | seq(u32) | len | payload
| crc32`, 상태 응답. 트렁케이트·과길이에 **hang 없이 재동기화**.

**실기 결과 (맥 ↔ Uno, 115200)**

| 시험 | 기대 | 실측 |
|---|---|---|
| 정상 프레임 ×3 | OK | **OK** |
| 페이로드 1비트 손상 | 거부 | **BAD_CRC** |
| 낡은 seq 재전송 | 거부 | **REPLAY** |
| 퍼징 800회(임의 바이트) | 오수용·hang 0 | **잘못 OK 0 · hang 없음** |
| 퍼징 후 정상 프레임 | OK | **OK**(생존) |

**정직한 임베디드 논의 — 왜 HMAC 이 없나.** udp-network-lab 은 스푸핑 방어로
HMAC-SHA256 을 쓰지만, ATmega328(8비트·2KB RAM·16MHz)엔 SHA256 이 무겁다. 그래서
여기선 **무결성(CRC32)+재전송(seq)만** 임베디드로 넣고 **인증(HMAC)은 상위 계층
(Pi/Host)** 이 담당하는 분담이 현실적임을 실측 크기(스케치 2130B/6% flash, RAM 228B)로
뒷받침한다. *"무엇을 MCU 에 얹고 무엇을 상위로 미룰지"* 가 이 조각의 교훈이다.
→ UDP · 로봇 · **임베디드**가 한 보안 줄기로 닫힌다.

## B — E-STOP 반응지연 〔안전〕

**무엇** — [RoboSec](robosec.md)·[컵 정렬](cup-sorting.md) 의 안전 계층(긴급정지)을
물리 계층에서 정량화했다. 점퍼 하나로 **D4(자극, active-low) ── D2(INT0, FALLING)**
를 잇고, `micros()` 로 D4 를 LOW 로 내린 순간 → D2 인터럽트 진입까지를 500회 잰다.

**실기 결과 (Uno, 500회)**

| 지표 | 값 |
|---|---|
| mean | **9.1 µs** |
| p50 / p95 / p99 | 8 / 12 / 12 µs |
| min / max | 8 / 16 µs |
| no-fire | 0 / 500 |

입력→반응 바닥은 **10 µs 안쪽**, 지터 ~0.

**정직한 한계.** `micros()` 분해능 4 µs 라 그 이하는 못 가르고, 측정값은
digitalWrite(~4µs)+인터럽트 지연에 지배된다. 점퍼는 깨끗한 에지라 **버튼 물리
바운스(수 ms)를 뺀 전자적 반응 바닥**이다. E-STOP 의 **엔드투엔드** 지연은 이 µs 급이
아니라 하류(액추에이터·통신·제어루프)가 지배한다 — 이 조각은 그 사슬의 **가장 빠른
끝**을 못박을 뿐이다. 상류 지연은 RoboSec·주행 제어에서 따로 다뤘다.

## C — USB-시리얼 링크 특성화 〔통신〕

**무엇** — robot-link-timing 의 시리얼 축을 정량 곡선으로 채웠다. 길이 기반
echo(`'L''T' len payload`)를 올리고 RTT·처리량을 **payload 크기**와 **baud** 두 축으로
스윕했다.

**결과 1 — vs payload (baud 115200)**: RTT 가 크기에 **선형**, 처리량 ~5 KB/s 로 포화.

| bytes | 1 | 8 | 32 | 64 | 128 | 200 |
|---|---|---|---|---|---|---|
| RTT mean(ms) | 3.15 | 4.40 | 8.80 | 14.51 | 26.14 | 39.05 |
| 처리량(KB/s) | 1.2 | 2.4 | 3.9 | 4.5 | 4.9 | 5.1 |

→ **반이중 요청-응답 구조**가 baud 원시대역폭보다 먼저 병목이다.

**결과 2 — vs baud (payload 8B)**: 9,600→26.78ms · 57,600→6.47 · 115,200→4.36 ·
250,000→3.30 · 1,000,000→**2.70ms**. 체감 감소 — 남는 **~2.5ms 바닥은 baud 가 아니라**
USB-CDC 폴 주기+호스트 스케줄링+루프 지연이다.

**핵심.** 작은 명령(로봇 제어처럼 수~수십 B)에선 **baud 를 올려도 ~2.5ms 아래로 못
간다** — 지연을 줄이려면 baud 가 아니라 **왕복 횟수·USB 스택**을 손봐야 한다.

## Verification

세 벤치 모두 **실제 Arduino Uno 하드웨어에서 실측**했다(맥 호스트, CH340, `arduino-cli`
빌드·플래시 + `pyserial` 프로브). A 는 정상·손상·재전송·퍼징 800회, B 는 500회 반복
분포, C 는 payload 6점·baud 5점 스윕. 위 표의 모든 숫자는 실측이며 시뮬레이션이 아니다.

## Limitations

- **A** — HMAC 미탑재(위 논의). 스푸핑은 이 계층 단독으로 못 막는다(상위 인증 전제).
  재전송 가드는 단조 seq 최근값 1개, 재정렬 창 미구현(호스트 ReplayGuard 참고).
- **B** — 전자적 반응 바닥만. 버튼 디바운스·엔드투엔드 정지시간은 범위 밖.
- **C** — 반이중 요청-응답만 측정(파이프라이닝 미측정). CH340·macOS 특성이라
  FTDI/native-USB·리눅스에선 오버헤드 바닥이 다를 수 있다.
- 셋 다 **단일 보드 벤치**다. 로봇 통합(실제 Pi↔STM32 링크 적용)은 하지 않았다.
