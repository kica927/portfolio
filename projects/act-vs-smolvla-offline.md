# ACT vs SmolVLA — 오프라인 정량 비교

> *2026-09 · 단독 · 로봇팔 트랙 확장(오프라인)*
>
> [LeRobot-imitation](lerobot-imitation.md)과 [SmolVLA-XPU](smolvla-xpu.md) 두 프로젝트가
> 공통으로 "미완료"로 남겨 둔 과제 — **"ACT와 SmolVLA를 같은 조건으로 비교"** — 를
> 실기 없이 오프라인 지표로 완성한다.

---

## Problem

기존 두 정책은 서로 다른 과제로 학습돼 있었다: ACT(`lsy0284/act_tape`)는 "테이프를
컵에 끼우기", SmolVLA(`kica927/smolvla_redball_ft`)는 "빨간 공을 집어 옮기기". 과제가
다르면 loss도 추론 지연도 나란히 놓을 수 없다.

로봇 실기(SO-ARM101)는 2026-09-08부로 접근이 끝나 성공률 비교는 불가능하다. 그러나
**같은 데이터셋([`kica927/redball`](https://huggingface.co/datasets/kica927/redball))으로
ACT를 처음부터 새로 학습**시키면, 학습 비용·수렴 형태·추론 지연이라는 오프라인
지표만큼은 SmolVLA와 정당하게 나란히 놓을 수 있다.

## Method

- 데이터: `kica927/redball` — 15 에피소드, 8,645 프레임, 30fps, 단일 과제("pick up the
  red ball and place it somewhere").
- **ACT** — 처음부터 학습. `lerobot-train --policy.type=act --policy.device=xpu
  --batch_size=4 --steps=20000`. 이미지 키 `followcam`.
- **SmolVLA** — [SmolVLA-XPU](smolvla-xpu.md)에서 이미 학습된 결과를 그대로 재사용
  (`--steps=6000`, 이미지 키 `camera1`로 rename).
- **추론 지연** — 더미 관측(480×640 RGB + 6차원 상태)으로 `policy.select_action()` 1회
  호출 시간을 30회 측정(warmup 5회). 매 반복 전 `policy.reset()`으로 액션 큐를 비워,
  청크 정책이 "큐에서 꺼내기"가 아니라 매번 실제 forward를 하도록 강제했다 — 그래야
  두 정책의 순수 추론 비용이 공평하게 비교된다.
- 실행: Intel Arc B580(XPU), lerobot 0.6.1, torch 2.11.0+xpu.

## Results

### 학습 비용 · 구조

| 항목 | ACT | SmolVLA |
|---|---|---|
| 파라미터(전체 / 학습가능) | 51.6M / 51.6M | 450.0M / 99.9M(비전 인코더 동결) |
| 학습 스텝 | 20,000 | 6,000 |
| 평균 처리 속도 | 12.40 step/s | ~9.8 step/s |
| 총 학습 시간 | 59분 56초 | ~12분 |
| 체크포인트 크기(단일) | 198 MB | 865 MB |

### Loss 수렴 (서로 다른 손실 구성 — 절대값 비교 불가, 궤적만 참고)

| ACT step | loss | | SmolVLA step | loss |
|---|---|---|---|---|
| 1K | 1.952 | | 50 | 0.615 |
| 5K | 0.529 | | 500 | 0.364 |
| 10K | 0.260 | | 1000 | 0.274 |
| 15K | 0.181 | | 2000 | 0.200 |
| 20K | **0.156**(l1 0.125·kld 0.003) | | 3000 | 0.138 |
| | | | 5000 | 0.099 |
| | | | 6000 | **0.096** |

### 추론 지연 (XPU, 단일 관측 → 액션, N=30)

| | 평균 | 중앙값 | 표준편차 |
|---|---|---|---|
| **ACT** | **6.48 ms** | 6.47 ms | 0.09 ms |
| **SmolVLA** | **143.64 ms** | 143.62 ms | 0.53 ms |

→ **SmolVLA가 ACT보다 약 22배 느리다.**

## Findings

1. **loss 절대값 비교는 무의미하다.** ACT는 L1+KLD 조합, SmolVLA는 VLM 기반 정책의
   손실 구성이 달라 같은 척도가 아니다. 유효한 비교는 "둘 다 단조 수렴한다"는 형태뿐이다.
2. **파라미터 규모 차이(8.7배)가 추론 지연 차이(22배)로 증폭된다.** SmolVLA는 500M
   VLM 백본(16 레이어로 축소했음에도)을 매 액션 산출마다 통과해야 해서, 학습가능
   파라미터가 ACT의 절반 수준(99.9M vs 51.6M)임에도 추론은 훨씬 무겁다.
3. **제어 주기 관점에서 실질적 차이다.** ACT의 6.48ms는 100Hz대까지 여유롭지만,
   SmolVLA의 143.64ms는 이론상 약 7Hz가 상한이다. [grippers](grippers.md)의 목표 제어
   주기(9.6Hz)에 근접·초과할 수 있는 수준 — VLA의 언어 지시 유연성은 실시간성과
   맞바꾼 것이다.
4. **체크포인트 크기(198MB vs 865MB, 4.4배)도 배포 관점의 실질 비용이다.** 엣지
   디바이스에 올릴 때 SmolVLA 쪽이 저장·전송 부담이 크다.

## 정직한 한계

- **스텝 수가 다르다(ACT 20,000 vs SmolVLA 6,000).** "동일 조건"이라 부르기엔
  완전하지 않다. SmolVLA의 6,000 step은 [SmolVLA-XPU](smolvla-xpu.md)에서 이미 수렴이
  확인된 값을 그대로 재사용했고, ACT는 처음부터 학습이라 더 많은 스텝이 필요하다고
  판단해 20,000으로 정했다. 두 정책을 정확히 같은 스텝 수로 맞춘 재실험이 이 비교의
  자연스러운 다음 단계다.
- **실기 성공률 비교는 여전히 못 한다**(하드웨어 접근 2026-09-08 종료). 이 비교는
  학습 비용·추론 지연이라는 간접 지표에 한정된다 — "느리다/빠르다"가 "실패한다/
  성공한다"를 보장하지 않는다.
- 추론 지연은 단일 프로세스에서 warmup 5회·반복 30회의 결과다. 여러 번 프로세스를
  재시작한 반복까지는 하지 않았다.
- ACT 학습 중(step 10K~15K 구간) 다른 두 프로젝트(엣지 AI 벤치마크·자율주행 인지모델)가
  같은 데스크탑에서 동시에 CPU를 점유해 step/s가 12.4→4 부근까지 떨어진 구간이 있다.
  최종 loss·파라미터 수·지연 측정 자체에는 영향이 없지만(측정은 학습 완료 후 별도
  실행), **총 학습 소요시간(59분 56초)은 이 리소스 경합의 영향을 받아 단독 실행보다
  길어졌을 수 있다.**

## 추가 실험 — SmolVLA를 OpenVINO로 경량화 시도 (2026-09-12)

[A1](a1-edge-opt.md)의 양자화 접근을 SmolVLA에도 적용해 143.64ms를 줄일 수 있는지
시도했다. **VLM 백본 + 액션 전문가 구조라 ONNX 변환 자체가 막힐 것으로 예상**했으나,
실제로는 예상과 다르게 흘러갔다.

**시도 순서와 결과**

1. `policy.select_action()`의 핵심 경로(`model.sample_actions()`)를 감싸 `torch.onnx.export`
   (legacy TorchScript exporter, opset 18)로 전체 파이프라인 export를 시도 — **예상외로
   성공.**
2. `dynamo=True`(최신 exporter)로도 재시도 — **역시 성공.**
3. 두 ONNX 중 하나(15.4MB)를 OpenVINO IR로 변환 — **이것도 성공.**
4. IR을 CPU·Arc B580(GPU.1)에서 실행해 지연을 측정:

| device | 결과 |
|---|---|
| CPU | **612.51ms**(mean) — PyTorch/XPU 베이스라인(143.64ms) 대비 **4.3배 느림** |
| Arc B580(GPU.1) | **컴파일 자체가 실패**(`ProgramBuilder` 단계에서 미지원 연산으로 추정되는 에러) |

**신뢰성 자체에 의문이 있다.** 변환된 IR의 Constant(가중치) 텐서 총합을 세어보니
**810.2M개**로, 원본 SmolVLA의 실제 파라미터 수(450.0M)와 맞지 않는다. 그런데도 ONNX
파일 크기는 15.4MB에 불과하다(450M 파라미터면 FP32 기준 1.8GB는 돼야 한다). 이 세
숫자(810.2M 텐서 원소·15.4MB 파일·143.64ms였던 원본과 무관하게 느려진 지연)가 서로
앞뒤가 맞지 않는다 — **export된 그래프가 원본과 동일한 계산을 하는지 검증하지
않았고, 출력값을 PyTorch 버전과 대조하지도 않았다.** "예상외로 export가 성공했다"는
사실 자체는 흥미롭지만, 그 결과물이 올바른 SmolVLA를 나타낸다고 확신할 근거가 없다.

**결론: 이 경로로는 경량화 이득을 얻지 못했다.** CPU에서는 명백히 느려졌고, GPU에서는
아예 실행이 안 되며, 결과물의 정합성도 검증되지 않았다. INT8 양자화(NNCF)는 이 시점에서
시도하지 않았다 — FP32 단계부터 이미 원본보다 느린 것을 양자화한들 개선을 기대하기
어렵고, 먼저 export 정합성 문제를 풀어야 의미가 있다.

## Future Work

- ACT·SmolVLA를 정확히 같은 스텝 수로 재학습해 학습 곡선 자체를 직접 비교.
- 실기 접근이 복구되면 성공률 비교로 이어서 완성.
- ~~OpenVINO/INT8 양자화로 SmolVLA 추론 경량화~~ → **시도했으나 미해결로 남음.** ONNX
  export 자체는 예상외로 됐지만 결과물의 정합성이 의심스럽고(파라미터 수 불일치),
  실제 지연은 오히려 4배 느려졌다(CPU) · GPU는 컴파일 실패. 다음에 이어서 할 것:
  (1) export된 그래프의 출력을 PyTorch 원본과 직접 대조해 정합성부터 검증, (2) 정합성이
  확인되면 GPU 컴파일 실패의 정확한 원인(미지원 연산자) 규명, (3) 그 이후에야 INT8
  양자화 의미가 있다.
