# 5G/UDP 종단간 통신 프로토타입

> **2023-07 ~ 2023-08 · 쉴드론(Shielddron) 인턴 · 철도 차량 간 이동통신**
>
> ⚠️ **코드는 공개하지 않습니다.** 재직 중 작성한 회사 자산이고, 실제 망 구성과
> IP 가 포함되어 있습니다. 이 문서는 **무엇을 했고 무엇을 배웠는가**의 기록이며,
> 같은 문제를 clean-room 으로 다시 푸는 것은 별도 프로젝트
> [`udp-network-lab`](../plans/roadmap.md#udp-network-lab) 으로 분리했습니다.

---

## 1. Problem

철도 차량의 RS-232 장비를 **차량 밖 원격 단말과 잇는 것**이 과제였습니다.
차량은 움직이므로 유선이 불가능하고, 두 끝단은 시리얼 장비이므로 그 사이를
IP 망으로 건너야 합니다.

## 2. Architecture

```
RS-232 장비
     │
     ▼
Serial-to-Ethernet 변환
     │
   UDP/IP
     ▼
  5G 모뎀
     │
     ▼
멀티캐스트 / 프록시 서버
     │
     ▼
  5G 모뎀
     │
     ▼
  원격 단말
```

**양방향입니다.** 한쪽 방향만 도는 것을 성공으로 세면 절반만 검증한 것이 됩니다.

## 3. My Contribution

- 기존 **패킷 프로토콜 분석** — 규격 문서를 읽고 각 필드가 왜 거기 있는지 파악
- 바이트 순서(리틀 엔디언)와 **CRC** 처리 구현
- 5G 모뎀 연동 및 망 초기화
- **PacketSender** 로 패킷을 직접 만들어 주입, **Wireshark** 로 실제 오간 것을 확인
- 양방향 통신 검증 및 디버깅
- PCB 설계(PADS), 4호선 차량 주간제어기 설계

## 4. 무엇을 배웠나

### 프로토콜을 먼저 읽고 의도를 파악한다

받은 지시는 "5G 모뎀으로 통신을 구현하라" 였지만, 먼저 한 것은 **정해져 있던
프로토콜을 분석해 어떤 의도가 담긴 시스템인지 파악하는 일**이었습니다. 필드
하나하나가 왜 있는지 모르는 상태에서 코드를 쓰면, 동작해도 왜 동작하는지 모릅니다.

### 안 보이는 계층을 볼 수 있게 만든다

시리얼 장비 두 대 사이에 변환기·모뎀·프록시 서버가 끼어 있으면, "안 된다"는
증상만으로는 어느 구간이 문제인지 알 수 없습니다. **PacketSender 로 임의 지점에
패킷을 넣고 Wireshark 로 어디까지 갔는지 보는 것**이 유일하게 확실한 방법이었습니다.

이 습관이 이후 로봇 프로젝트에서 그대로 이어집니다 — Host↔Pi 링크를 디버깅할 때도
같은 방식을 씁니다.

### 프로토콜을 만든 사람과 서버를 운영하는 사람은 다른 사람이다

패킷 전송 시험을 진행할 때 서버 관리자와 프로토콜 설계자 양쪽과 계속 소통해야
했습니다. **한쪽만 보고 고치면 다른 쪽에서 깨집니다.**

## 5. 이 경험이 지금과 이어지는 곳

| 그때 | 지금 |
|---|---|
| UDP 로 시리얼 장비를 잇는다 | UDP 로 Host PC 와 로봇을 잇는다 |
| 바이트 순서 · CRC | JSON 5필드 · 손상 패킷 폐기 정책 |
| Wireshark 로 실제 오간 패킷 확인 | 로그 타임스탬프로 제어 주기 실측 |
| 프로토콜을 읽고 의도를 파악 | 프로토콜에 **없는 것**(시퀀스 번호·인증)이 무엇을 뜻하는지 묻기 |

마지막 행이 [`robosec`](../plans/robosec/threat_model.md) 의 출발점입니다.

## 6. Limitations

- 코드가 없으므로 **이 문서는 검증할 수 없는 서술**입니다. 그래서 같은 문제를
  다시 푸는 `udp-network-lab` 을 로드맵에 넣었습니다.
- 성능 수치를 기록해 두지 않았습니다. 당시에는 "동작한다"가 목표였고, 처리율과
  지연 분포를 재야 한다는 생각을 하지 못했습니다.
