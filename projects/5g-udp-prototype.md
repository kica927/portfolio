# 5G/UDP 종단간 통신 프로토타입

> **2023-07 ~ 2023-08 · 쉴드론(Shielddron) 인턴 · 철도 차량 간 이동통신**
>
> ⚠️ **코드는 공개하지 않습니다.** 재직 중 작성한 회사 자산이고, 실제 망 구성과
> IP 가 포함되어 있습니다. 이 문서는 **무엇을 했고 무엇을 배웠는가**의 기록이며,
> 같은 문제를 clean-room 으로 다시 푸는 것은 별도 프로젝트
> [`udp-network-lab`](../plans/roadmap.md#udp-network-lab) 으로 분리했습니다.

---

## 1. Problem

철도 차량의 RS-232 장비를 **차량 밖 원격 단말과 잇는 것**이 과제였습니다.
차량은 움직이므로 유선이 불가능하고, 두 끝단은 시리얼 장비이므로 그 사이를
IP 망으로 건너야 합니다.

## 2. Architecture

```
RS-232 장비
     │
     ▼
Serial-to-Ethernet 변환
     │
   UDP/IP
     ▼
  5G 모뎀
     │
     ▼
멀티캐스트 / 프록시 서버
     │
     ▼
  5G 모뎀
     │
     ▼
  원격 단말
```

**양방향입니다.** 한쪽 방향만 도는 것을 성공으로 세면 절반만 검증한 것이 됩니다.

## 3. My Contribution

- 기존 **패킷 프로토콜 분석** — 규격 문서를 읽고 각 필드가 왜 거기 있는지 파악
- 바이트 순서(리틀 엔디언)와 **CRC** 처리 구현
- 5G 모뎀 연동 및 망 초기화
- **PacketSender** 로 패킷을 직접 만들어 주입, **Wireshark** 로 실제 오간 것을 확인
- 양방향 통신 검증 및 디버깅
- PCB 설계(PADS), 4호선 차량 주간제어기 설계

## 4. 무엇을 배웠나

### 프로토콜을 먼저 읽고 의도를 파악한다

받은 지시는 "5G 모뎀으로 통신을 구현하라" 였지만, 먼저 한 것은 **정해져 있던
프로토콜을 분석해 어떤 의도가 담긴 시스템인지 파악하는 일**이었습니다. 필드
하나하나가 왜 있는지 모르는 상태에서 코드를 쓰면, 동작해도 왜 동작하는지 모릅니다.

### 안 보이는 계층을 볼 수 있게 만든다

시리얼 장비 두 대 사이에 변환기·모뎀·프록시 서버가 끼어 있으면, "안 된다"는
증상만으로는 어느 구간이 문제인지 알 수 없습니다. **PacketSender 로 임의 지점에
패킷을 넣고 Wireshark 로 어디까지 갔는지 보는 것**이 유일하게 확실한 방법이었습니다.

이 습관이 이후 로봇 프로젝트에서 그대로 이어집니다 — Host↔Pi 링크를 디버깅할 때도
같은 방식을 씁니다.

### 프로토콜을 만든 사람과 서버를 운영하는 사람은 다른 사람이다

패킷 전송 시험을 진행할 때 서버 관리자와 프로토콜 설계자 양쪽과 계속 소통해야
했습니다. **한쪽만 보고 고치면 다른 쪽에서 깨집니다.**

## 5. 측정 — 3년 뒤에 원자료에서 읽어낸 것

> 이 절은 **2026-08-30 에 추가**했습니다. 당시 남겨 둔 트래픽 로그와 시험 메모를
> 다시 열어 읽은 결과입니다. 로그 파일 자체는 실제 운영 IP 를 담고 있어 공개하지
> 않고, 여기에는 **거기서 계산한 값과 결론만** 옮깁니다.

### 왕복 지연 — 정상 상태와 콜드 스타트는 다른 값이다

PacketSender 트래픽 로그에 밀리초 타임스탬프가 찍혀 있었습니다. 보낸 것과 같은
페이로드가 되돌아온 쌍을 골라 왕복 시간을 계산했습니다.

| 세션 | 왕복 |
|---|---|
| A | **32 ms** · **31 ms** |
| B | **41 ms** · **40 ms** |
| B — 첫 패킷 | **12,219 ms** |

정상 상태는 30~40 ms 로 안정적입니다. 그런데 **한 세션의 첫 패킷만 12.2 초**입니다.
5G 모뎀이 세션을 세우는 동안의 지연으로 보입니다.

이것이 뜻하는 바가 있습니다 — **"왕복 지연이 얼마인가"에 답이 하나일 수 없습니다.**
정상 상태 40 ms 만 말하면 첫 패킷을 기다리는 12 초를 숨기는 것이고, 평균을 내면
둘 다 아닌 값이 나옵니다. 링크 위에 무언가를 얹으려면 **콜드 스타트 구간을 따로
다뤄야 한다**는 뜻입니다.

지금 grippers 에서 Host↔Pi 링크에 워치독을 두고 첫 연결과 재연결을 정상 통신과
구분해 다루는 것이 같은 문제입니다.

표본이 다섯 쌍뿐이라 **분포는 말할 수 없습니다.** 백분위수를 내려면 수백 회를
찍었어야 했는데 그러지 않았습니다.

### 페이로드는 전부 1472 바이트였다

서버 로그의 모든 패킷이 `data_size:1472` 입니다.

```
1500 (이더넷 MTU) − 20 (IP 헤더) − 8 (UDP 헤더) = 1472
```

**IP 단편화가 일어나지 않는 최대 크기**입니다. 당시에는 규격에 그렇게 적혀 있어
따랐을 뿐인데, 지금 보면 이 숫자 하나가 "단편화된 UDP 는 조각 하나만 잃어도
전부 잃는다" 는 판단의 결과였습니다.

## 6. 고의 오류 주입 — 그때는 몰랐지만 위협 모델이었다

시험 메모에 `*에러 TEST용 패킷` 이라는 절이 있었습니다. 필드를 하나씩 일부러
깨뜨리고 수신 측이 어떻게 반응하는지 적어 둔 표입니다.

| 깨뜨린 것 | 수신 측 반응 |
|---|---|
| 장비 ID 가 다름 | 상관 없음 — 그대로 처리 |
| 시퀀스 번호가 틀림 (중복 · 역행 · 건너뜀) | 상관 없음 |
| **CRC32 가 틀림** | **상관 없음** |
| 길이 필드가 실제와 다름 | 상관 없음 |
| 메시지 크기가 규격보다 큼 | **전송 불가** |

당시 저는 이 표를 **"이렇게 해도 동작하더라"** 로 읽었습니다. 목표가 "통신이
되게 하는 것" 이었으니까요. 지금 같은 표를 다시 읽으면 이렇게 됩니다.

- **CRC32 를 검사하지 않는다** → 손상된 패킷과 **조작된 패킷**이 구분되지 않는다
- **시퀀스를 검사하지 않는다** → 재전송(replay)이 막히지 않고, 순서 역전이 그대로 반영된다
- **ID 를 검사하지 않는다** → 다른 장비를 사칭해 패킷을 넣을 수 있다
- 유일하게 막힌 것은 **길이**뿐이고, 그것도 보안 장치가 아니라 버퍼 제약으로 보인다

즉 이 프로토콜에는 **무결성 검증도, 재전송 방지도, 발신자 인증도 없었습니다.**
CRC32 필드가 **존재하는데 검사되지 않는다**는 점이 특히 그렇습니다 — 있는 것과
집행되는 것은 다릅니다.

움직이는 철도 차량과 원격 단말 사이를 잇는 링크였다는 것을 생각하면, 이 표는
그 자체로 위협 목록입니다. **다만 그때 저는 그렇게 읽지 못했습니다.**

이 경험이 [`robosec`](../plans/robosec/threat_model.md) 의 출발점입니다. 거기서
찾으려는 것이 정확히 같은 종류의 결함이거든요 — **크래시를 내지 않고, 테스트를
통과하고, 그래서 아무도 문제라고 부르지 않는 것.**

## 7. 이 경험이 지금과 이어지는 곳

| 그때 | 지금 |
|---|---|
| UDP 로 시리얼 장비를 잇는다 | UDP 로 Host PC 와 로봇을 잇는다 |
| 바이트 순서 · CRC | JSON 5필드 · 손상 패킷 폐기 정책 |
| Wireshark 로 실제 오간 패킷 확인 | 로그 타임스탬프로 제어 주기 실측 |
| 프로토콜을 읽고 의도를 파악 | 프로토콜에 **없는 것**(시퀀스 번호·인증)이 무엇을 뜻하는지 묻기 |
| 필드를 깨뜨려 반응을 표로 적음 | 같은 표를 **위반 목록**으로 다시 읽기 (I1–I8) |

마지막 행이 [`robosec`](../plans/robosec/threat_model.md) 의 출발점입니다.

## 8. Limitations

- **코드는 공개하지 않습니다.** 회사 자산이고 실제 망 구성이 들어 있습니다. 같은
  문제를 clean-room 으로 다시 푸는 `udp-network-lab` 을 로드맵에 넣은 이유입니다.
- **원자료도 공개하지 않습니다.** 트래픽 로그와 서버 로그에 실제 운영 IP 가 그대로
  남아 있습니다. 5~6장의 표는 그 로그에서 계산한 값이며, 검증하시려면 로그를
  직접 보여 드리는 수밖에 없습니다.
- **표본이 적습니다.** 왕복 지연은 다섯 쌍뿐이라 평균은 말할 수 있어도 분포나
  꼬리 지연은 말할 수 없습니다. 처리율은 아예 재지 않았습니다.
- **오류 주입 표에 빈칸이 있습니다.** `NID_SENSOR` 를 어긋나게 한 경우의 결과가
  적혀 있지 않습니다. 시험을 했는데 안 적은 것인지, 아예 안 한 것인지 지금은
  알 수 없습니다.
- **이 문서의 5~6장은 3년 뒤에 쓴 것입니다.** 당시에 이렇게 이해하고 있었다는
  뜻이 아니라, 그때 남긴 기록을 지금의 눈으로 다시 읽은 결과입니다. 그 차이 자체가
  이 문서에서 제가 말하고 싶은 것이기도 합니다.
