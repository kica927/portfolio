# 색상별 컵 정렬 — SO-ARM101 로봇팔 미니 프로젝트

> 📍 이 프로젝트는 [SO-ARM101 로봇팔 트랙](soarm-robotarm-track.md)의 한 단계입니다.

> Intel Physical AI 로봇팔 교육의 **FINAL 미니 프로젝트**. 색이 섞여 한 스택으로
> 쌓인 컵 6개(Red·Blue·Yellow 각 2개)를, 카메라로 맨 위 컵의 색을 인식해
> 색상별 스택 3곳으로 다시 쌓는다.
>
> 코드: `cup.py`(비전) · `calibrate_homography.py`(캘리브레이션) ·
> `cup_stacking.py`(통합·안전, 320줄)

**한 줄 요약**: 파지 정확도보다 **안전 불변식**(긴급정지·지연 대응·도달 한계 거부)에
무게를 둔 프로젝트. grippers 로 이어지는 "실패를 상태로 다룬다"는 사고가 여기서 시작됐다.

---

## 1. 문제

- **시작**: Red/Blue/Yellow 컵 2개씩, 총 6개가 색이 섞인 채 한 스택으로 쌓여 있다.
- **목표**: 색상별로 지정된 3곳에 각각 2개씩 다시 쌓는다.
- **제약**: 매 픽업마다 소스 스택은 한 개 줄고 목적지 스택은 한 개 는다 → **집는
  높이와 놓는 높이가 매번 달라진다.**

## 2. 파이프라인

```
카메라 ROI → 맨 위 컵 색·픽셀좌표 인식 (cup.py::detect_color)
        → 호모그래피로 pixel→robot 좌표 변환 (H)
        → 색상별 목적지 스택 위로 이동·적재
        → 소스/목적지 스택 높이(Z)를 CUP_H 단위로 갱신
```

이동은 **항상 안전고도(`Z_HOVER`)를 경유**한다. `arm.go()` 를 "들어올리기 →
수평이동 → 내리기" **3단계로 쪼개** 호출해, 이동 중 다른 컵과 충돌하지 않게 했다.

> 이 "항상 waypoint 를 거쳐 이동한다"가 grippers 의
> [팔 경로 안전 규칙](grippers.md)과 같은 원칙이다 — 바닥 높이에서 수평으로
> 쓸고 가지 않는다.

## 3. My Contribution — 안전/시스템

이 프로젝트에서 제가 맡은 것은 **안전 계층**이었고, 과제 슬라이드의 요구사항
세 가지를 코드로 옮겼다.

### 긴급정지 (`EStop` 클래스)

카메라 창에서 `e`/`SPACE` → **전 서보(1~6) 토크 즉시 OFF**, 이동 루프 정지.
`r` 로 재활성화 후 재개, `q` 로 종료. 핵심은 **이동 시퀀스의 각 스텝 사이마다
`estop.check()` 를 호출**한다는 것 — 이동 도중에도 즉시 멈춘다.

```python
def move_cup(src_xy, src_level, dest_xy, dest_level, drv, estop, color):
    ...
    for step in (lift, traverse, lower):
        estop.check(drv)     # 매 스텝 전 비상정지 확인
        arm.go(step, ...)
```

### 지연(딜레이) 대응 — 모르면 움직이지 않는다

매 프레임 타임스탬프를 기록하고, 정상 프레임을 못 받은 시간이 `DELAY_LIMIT_S`
(0.35 s)를 넘으면 **"지연"으로 판정해 새 이동 명령을 절대 내리지 않고**
안전고도에서 대기한다.

```python
if now - last_good_frame_t > DELAY_LIMIT_S:
    print("[DELAY] 카메라 프레임 지연 감지 — 안전 고도 대기 중")
    # 새 이동 명령을 내리지 않는다
```

`--sim-delay 0.5` 로 인위적 지연을 주입해 이 동작을 발표 데모로 보여줄 수 있게 했다.

> **이것이 grippers 의 링크 워치독과 정확히 같은 사고다** — 오래된/없는 입력을
> "0(정지)"으로 오해하지 않고, "모른다"로 두고 안전측으로 행동한다.

### 제어 한계 거부 (`demo_reach_limit`)

IK(`ik_core.py`)가 팔이 닿을 수 없는 좌표를 받으면 `ValueError` 로 **이동을
거부**한다. 프로그램 시작 시 작업반경 밖 좌표를 일부러 한 번 시도해 거부 로그를
보여준다. 관절 각도 한계는 `real.py` 의 `_clamp_arm` 에서 소프트 클램프된다.

> grippers 의 **"제자리회전에 병진이 섞이면 거부"**(D2), **관절 절대 한계**(D8)와
> 같은 계열 — 애매하면 추측해서 실행하지 않고 거부한다.

## 4. 캘리브레이션 — 손으로 티칭

`calibrate_homography.py` 는 **토크를 끄고 사람이 팔을 손으로 움직여**(torque off)
네 곳 이상의 좌표를 티칭한 뒤, 그 대응으로 pixel→robot 호모그래피 `H` 를 계산한다.
값을 타이핑해 넣는 게 아니라 실제 팔을 옮겨 잡는 방식이다.

> grippers 의 관절 캘리브레이션 도구도 같은 방식이다 — 토크를 풀어 손으로 옮긴다.

## 5. 측정해야 하는 값들 (정직하게: 상당수 `# TODO 측정`)

코드 상단에 캘리브레이션 파라미터를 전부 모아 두고 `# TODO 측정` 으로 표시했다.

| 파라미터 | 측정 방법 |
|---|---|
| ROI · HSV 임계값(R/B/Y) | 실제 컵으로 `cup.py` 돌리며 조정 |
| `H` (호모그래피) | 4곳 이상 티칭 후 계산 |
| `CUP_H` · `CUP_R` | 자로 실측 |
| `GRIP_OPEN/CLOSE` | 놓치지도 찌그러뜨리지도 않는 값 탐색 |
| `Z_HOVER` | `max(스택수) × CUP_H + 여유` |
| `DELAY_LIMIT_S` | 정상 프레임 주기 측정 후 여유 |

## 6. 기존 코드 재사용

바닥부터 짜지 않고 교육용 `soarm_lab` 스택을 재사용했다. 무엇을 어디에 썼는지
매핑을 개발문서에 표로 남겼다 — `arm.go()`, `grasp.approach_xy()`(공 반지름을
컵 반지름으로만 교체), `IKSo101.solve(down=True)`, `RealBackend._clamp_arm`,
`driver_sdk` 의 서보 제어. **비전(빨간 공 검출)에서 컵 검출로 넘어올 때 색 임계값과
반지름만 바꾸면 됐다**는 게 재사용 설계의 이점이었다.

## 7. Limitations

- **파지 성공률을 측정하지 않았다.** 미니 프로젝트라 "정렬이 된다"까지가 목표였고,
  20회 중 몇 회 성공 같은 수치를 남기지 않았다.
- **파라미터 상당수가 `# TODO 측정`으로 남았다.** 데모는 됐지만 실측으로 굳힌 값이
  아니라 그날 현장에서 맞춘 값이다.
- **단일 조명·고정 배치 전제.** 조명이 바뀌면 HSV 임계값이 깨진다.

## 8. 이 프로젝트가 grippers 로 이어진 곳

| 컵 정렬 | grippers |
|---|---|
| 지연 시 새 명령 안 냄, 안전고도 대기 | 링크 워치독 — `None`은 정지가 아니라 "모른다" |
| 이동을 lift→traverse→lower 3단계로 | 팔은 waypoint 경유, 바닥에서 쓸지 않음 |
| 닿을 수 없는 좌표는 `ValueError` 거부 | "모르면 실패" — 회전+병진 거부, 관절 절대한계 |
| 긴급정지 = 전 서보 토크 OFF | E-STOP 을 상태와 무관하게 매 사이클 확인 |
| 손으로 티칭(torque off) | 관절 캘리브레이션도 손으로 |

컵 정렬은 작은 과제였지만, **"실패와 불확실을 어떻게 안전하게 다루는가"** 라는
grippers 의 중심 질문이 여기서 먼저 나타났다.
