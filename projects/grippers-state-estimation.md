# grippers 상태 추정 — 녹화 bag 으로 센서 퓨전과 SLAM 다시 보기

> *2026-09 · 단독 · grippers 확장(오프라인, 실기 없음)*
>
> [grippers](grippers.md) 로봇 하드웨어 접근은 2026-09-08 에 끝났다. 그 전날 녹화한 **실기 미션
> ros2 bag 두 개**(9분 · 10분)만으로 오도메트리 · IMU · LiDAR 를 다시 분석했다. 로봇 위에서는
> "돌아가니까" 넘어갔던 추정 파이프라인이, 데이터로 재 보니 **어디서 얼마나 틀리는지**를 정량화했다.

---

## Problem

grippers 는 Host 가 경로와 위치를 맡고, 로봇 쪽에서는 `/odom_raw` · IMU · LiDAR 가 나온다.
실기 디버깅 중에 이미 **`/odom_raw` 는 바퀴 인코더가 아니라 명령을 적분한 값**이고, STM32 펌웨어에
인코더 피드백 자체가 없다는 것을 확인했었다([grippers 6-5, 6-6](grippers.md)).

그러면 남는 질문은 이것이다.

1. 명령 적분 오도메트리는 실제 움직임을 **얼마나** 못 따라가는가
2. IMU 와 LiDAR 로 무엇을 되살릴 수 있는가
3. 표준 도구(`robot_localization` EKF, `slam_toolbox`)를 그대로 붙이면 **잘 되는가**

## Data

| bag | 길이 | 주요 토픽 |
|---|---|---|
| `run_20260905_150105` | 548 s | `/odom_raw` 48Hz · `/imu_raw` 48Hz · `/scan_raw` 10Hz (LD19, 360°) · `/cmd_vel` |
| `run_20260905_151233` | 618 s | 같음 |

영상 · 포인트클라우드는 용량 때문에 녹화에서 뺐다. 로봇은 Humble 로 녹화했고 분석은 데스크탑
(Ubuntu 24.04 · ROS 2 Jazzy)에서 했다. 정답 위치(모션 캡처 등)는 **없다.**

## 1. 오도메트리는 명령 그 자체다 — 정량 재확인

| 확인 | 결과 |
|---|---|
| `/odom_raw` 속도값 종류 | **4종류**, `/cmd_vel` 4종류와 100% 같음 |
| 시간차 0 에서 명령과 일치 | **99.86%** |
| 바퀴 관절 `/joint_states` | 9분 내내 0, 속도 필드 비어 있음 |

명령도 특이했다. 회전을 **±0.4 rad/s 펄스로 켰다 껐다** 하며 조향한다(9분 동안 명령 전환 1,670번,
평균 0.33초). 옆으로 가는 명령(`vy`)은 한 번도 없었다.

## 2. 회전 동역학 식별 — IMU 기준

정지 구간 IMU 자이로는 표준편차 **0.0025 rad/s** 로 조용했고, 바이어스는 두 bag 에서 0.00376 / 0.00393
rad/s 로 일관됐다. 이 IMU 를 기준으로 "명령 → 실제 회전" 을 `지연 τ + 1차 시정수 T + 게인 K` 로 식별했다.

| | bag 1 | bag 2 |
|---|---|---|
| τ / T / K | 0.02 s / 0.50 s / 0.935 | 0.02 s / 0.56 s / 0.933 |
| 모델 R² | **0.691** | **0.681** |
| 교차검증 R² (다른 bag 파라미터) | 0.690 | 0.680 |
| **"명령 = 실제" 가정 R²** | **−0.155** | **−0.171** |

명령 오도메트리가 전제하는 "명령이 곧 실제 회전"은 **평균값 하나로 찍는 것보다도 못하다**(R² 음수).
시정수 0.5초인 시스템을 0.33초 간격 펄스로 켜고 끄니 로봇이 명령을 끝까지 따라가지 못한다.
T 는 0.3~0.8 s 사이에서 R² 차이가 0.006 이내라 **범위로만** 정해진다(T 가 커지면 K 가 1 로 가며 상쇄).

## 3. LiDAR — URDF 가 틀렸다

직접 짠 2D ICP 로 연속 스캔을 맞춰 LiDAR 오도메트리를 만들었다.

- **LiDAR 기준 로봇 전진 방향은 81.5° / 83.4°** 였다. URDF 의 LiDAR 회전은 0° 다. SLAM 에서는
  기계적 장착을 90° 로 보고 −90° 로 보정했다.
- 스캔 점 개수가 496~504 개로 매번 달라, `slam_toolbox` 입력용으로 1° 간격 360 점 재샘플 노드를 넣었다.
- 자작 ICP 는 회전을 IMU 대비 **약 40% 작게** 추정했다. 로봇 자기 몸체를 빼 봐도 그대로였고(기각),
  IMU 회전을 초기값으로 주자 0.58 → 0.75 로 좋아졌다. 점대점 ICP 의 수렴 한계로 보고 **표준 도구로 넘어갔다.**

**판정 보류 — LiDAR 기울기.** 8월 26일 실측 기록은 LD19 가 높이 140mm, **11.3° 아래로** 기울어
정면 0.70m 에서 바닥에 닿는다고 한다. 그런데 9월 5일 bag 에서는 추정한 정면 방향으로 **최대 1.05~1.09 m**
까지 보였다. 이후 장착이 바뀌었을 수 있지만 하드웨어가 없어 확인할 수 없다.

## 4. EKF 를 그대로 붙이면 — 네 가지 구성

`robot_localization` EKF 에 입력 조합만 바꿔 넣었다.

| 구성 | 병진 | 회전 | 누적 회전 (EKF / IMU) | 순회전 (EKF / IMU) |
|---|---|---|---|---|
| A | 명령 | 명령 | **0°** / 2,779° | 0° / +112° |
| B | 명령 | IMU | 2,852° / 2,779° | **+231°** / +112° |
| C | 명령 | 명령 + IMU | 1,512° / 2,779° | +75° / +112° |
| **D** | 명령 | **바이어스 보정 IMU** | 2,802° / 2,779° | **+113° / +112°** |

(bag 1. bag 2 도 같은 양상: D 순회전 +94° / IMU +95°)

**A 가 회전을 한 번도 반영하지 못한 이유 — 공분산 설계.** `/odom_raw` 의 공분산을 속도 상태별로 세면:

| 명령 상태 | 회전속도 공분산 |
|---|---|
| 정지 | **1e-9** ("확실히 멈춤") |
| 회전 · 직진 | 1000 ("회전속도는 믿지 마라") |

드라이버가 **명령만 보고** 정지를 확신한다. 회전 중에는 명령을 무시하고, 펄스 사이 "정지" 구간에는 로봇이
관성으로 돌고 있어도 회전을 0 으로 강제한다. C 에서는 이 "확실히 정지" 가 IMU 까지 눌러 회전의 절반이 사라졌다.

**B 의 119° 드리프트 — 바이어스.** EKF B 는 IMU 측정을 빠짐없이 반영했다(누적 비율 1.026). 차이는
**자이로 바이어스를 EKF 에 알려 주지 않은 것** 뿐이었다. 0.00376 rad/s × 544 s = 2.05 rad = **117°** 로
순회전 차이 119° 와 맞는다. robot_localization 은 자이로 바이어스를 추정하지 않으므로, 정지 구간에서 잰
바이어스를 빼는 노드를 앞에 두자(D) IMU 적분과 1° 이내로 맞았다.

## 5. 평가 — 기준 궤적부터 의심하기

정답이 없어 `slam_toolbox` 지도 위 포즈를 기준으로 썼다. 그런데 SLAM 도 오도메트리를 사전 추정값으로 쓴다.
**기준이 사전 추정값 쪽으로 끌려가면 그 추정원이 유리해진다.** 그래서 사전 추정값과 스캔 처리 조건만 바꾼
기준끼리 먼저 비교했다.

| 기준끼리 차이 (bag 1 / bag 2) | 1초 방향 RPE | 방향 RMSE | 최종 방향 |
|---|---|---|---|
| 사전 추정값만 다름 (명령 vs 117° 흐르는 EKF B), 모든 스캔 처리 | 3.4° / 3.3° | 12.1° / 6.3° | 19.6° / 10.6° |
| 스캔 처리 임계값만 다름 (모든 스캔 vs 기본 2cm·2.9°) | 5.9° / 6.0° | 19.9° / 31.7° | 35.5° / 58.9° |

- 117° 흐르는 사전 추정값을 줘도 기준은 최종 10~20° 만 달라졌다. 스캔매칭이 대부분 바로잡지만 **완전히 독립적이지는 않다.**
- 기본 임계값은 2cm · 2.9° 미만 움직임의 스캔을 건너뛰어, 그동안 기준이 사전 추정값을 그대로 따라간다.
  **모든 스캔을 처리한 기준만** 평가에 썼다.
- 실제로 같은 IMU 적분의 1초 방향 RPE 가 명령 사전 추정 기준에서는 4.1°, EKF B 기준에서는 1.6° 로 나왔다.

그래서 **기준 2종 × bag 2개 모두에서 같은 방향이고, 기준 간 차이보다 큰 차이만** 결론으로 삼았다.

| 추정원 | ATE (m) | 5초 방향 RPE | 방향 RMSE |
|---|---|---|---|
| 명령 오도메트리 | 0.38 / 0.49 | 10.1° / 10.0° | 33.7° / 40.8° |
| EKF A | 2.97 / 3.16 | 32.1° / 31.1° | 73.7° / 87.5° |
| EKF C | 2.73 / 2.86 | 25.0° / 24.0° | 75.9° / 91.5° |
| **EKF D (바이어스 보정)** | **0.21 / 0.28** | **5.9° / 5.5°** | 41.5° / 43.8° |

(명령 사전 추정 · 모든 스캔 기준, bag 1 / bag 2. EKF B 사전 추정 기준에서도 D 의 ATE 0.24 / 0.28 m)

| 결론 | 판정 |
|---|---|
| EKF A · C 는 방향이 무너진다 (방향 RMSE 74~95°) | ✅ 확실 |
| 바이어스 보정 EKF D 의 위치 오차가 가장 작다 (명령 대비 0.1~0.2 m) | ✅ 기준 간 차이(0.06~0.07 m)보다 큼 |
| 5초 방향은 D · IMU 가 명령보다 정확하다 | ✅ 명령에 유리하게 기운 기준에서도 5.5~5.9° vs 10.0~10.1° |
| 1초 방향은 IMU 가 명령보다 약간 낫다 | ⚠️ 4.08° vs 4.38°, 차이가 작다 |
| 9분 장기 방향 우열 | ❌ 판정 불가 — 모든 추정원이 33~118° 틀리고 기준끼리도 10~20° 다르다 |

## 6. 식별한 모델 위에서 조향 제어기 비교

2절의 회전 모델에 grippers 실기 기록의 **회전 데드밴드**(0.35 rad/s 미만 명령은 안 돎,
[grippers 6-5](grippers.md))를 더해 시뮬레이터를 만들었다. bag 명령을 넣으면 IMU 를 **R² 0.691** 로
재현한다(식별값과 같음). bag 명령은 전부 ±0.4 라 데드밴드 자체는 이 데이터로 확인되지 않는다.

과제: 방향 30° / 90° / 180° 정렬, 허용 5°(grippers 기준) · 0.5초 유지 = 정착, Host 10Hz.
제어기는 항상 공칭 모델(T 0.5 · K 0.93)을 가정하고 실제 플랜트만 T 0.3~0.8 · K 0.8~0.93 으로 바꿨다.

| 제어기 | 규칙 |
|---|---|
| bang-bang | 허용 밖이면 ±최대 명령 (grippers 실기 방식) |
| 비례 | `u = kp·오차`, 포화, 0 이 아니면 최소 0.35 로 올림(데드밴드 보상) |
| MPC | 1.5초 예측, 명령 제약, 매 주기 박스 제약 최소제곱, 같은 데드밴드 보상 |

**첫 비교는 불공정했다.** bang-bang 은 최대 0.4, 나머지는 0.6 이라 180° 과제에서 bang-bang 만 제한 시간(8초)을
넘겨 실패했다. 제어 구조가 아니라 속도 한계가 결과를 정했다. 최대 명령을 맞추고 제한을 15초로 늘려 다시 쟀다.

- **최대 0.4 에서는 네 제어기가 사실상 같다** — 정착시간 차이 0.3초, 오버슈트 차이 0.5° 이내.
  데드밴드 0.35 와 최대 0.4 사이가 0.05 rad/s 뿐이라 연속 제어기도 켰다 끄는 동작으로 퇴화한다.
- **데드밴드 크기를 바꾸면**(최대 0.6, 공칭 플랜트):

| 정착시간 합(30+90+180°) / 최대 오버슈트 / 명령 전환 합 | 데드밴드 0 | 데드밴드 0.35 |
|---|---|---|
| bang-bang ±0.6 | 13.0 s / 7.1° / 12 | 13.0 s / 7.1° / 12 |
| 비례 kp=1 | 11.1 s / **2.9°** / **6** | 16.0 s / 5.6° / 12 |
| MPC | **10.5 s** / 3.8° / 9 | 13.8 s / 6.2° / 12 |

데드밴드가 없으면 비례 제어의 오버슈트 · 전환이 bang-bang 의 절반 이하가 되고 MPC 가 가장 빨리 정착한다.
**데드밴드 0.35 에서는 그 이점이 거의 사라진다.** 느린 플랜트(T 0.8)에서는 데드밴드와 무관하게 MPC 가
가장 빨랐다(15.2~15.8 s, bang-bang 19.3 s). 추세가 매끄럽지는 않다 — 데드밴드 0.2 에서 MPC 가 공칭 플랜트에서
오히려 느려졌는데(15.0 s), 제어기 모델에 데드밴드가 없어 보상 동작과 예측이 어긋난 영향으로 본다.

**결론: 이 플랫폼의 조향은 제어기보다 데드밴드가 성능 상한을 정한다.** 데드밴드를 줄이는 쪽(모터 드라이버
저속 보상 등)이 먼저고, 그 다음에야 비례 · MPC 가 의미 있는 차이를 낸다.

**틀린 예상도 남긴다.** bang-bang 이 5° 허용 안에서 계속 진동할 거라 봤지만, 모델에서는 오버슈트 약 5° 뒤
반대 펄스 한 번으로 정착했다. bag 에서 명령이 1,670 번 바뀐 것은 이 단순 조향 모델로 설명되지 않는다
(실제 Host 로직은 다른 상태 전환을 함께 섞는다).

## 무엇이 틀렸었나

| 판단 | 실제 |
|---|---|
| URDF 의 센서 장착값은 맞을 것 | LiDAR 방향이 약 90° 틀림. 기울기도 기록과 데이터가 어긋남 |
| 고정 거리 패턴 = 기울어진 LiDAR 가 보는 바닥 | 3cm 거리의 로봇 자기 몸체였다. 이걸로 피팅한 기울기 45° 는 버렸다 |
| ICP 회전 과소추정 = 자기 몸체가 섞여서 | 근거리를 넓게 빼도 그대로. 기각 |
| EKF B 붕괴 = 늦게 도착한 IMU 측정 누락 | 누락 없음(비율 1.026). 원인은 바이어스 |
| RPE 중앙값으로 비교 | 대부분 정지 · 제자리 회전이라 중앙값이 0 cm. 이동 구간 RMSE 로 교체 |
| 60초 시험에서 명령이 IMU 보다 좋아 보임 | 기준이 명령 쪽으로 기운 결과. 기준 민감도 실험으로 판정 불가 영역임을 확인 |

도구 쪽에서도 막혔다. `slam_toolbox` (Jazzy)는 lifecycle 노드라 `configure → activate` 전이 없이는 스캔을
구독조차 하지 않는다. 경고 없이 조용히 아무것도 하지 않아, 토픽 구독자 목록을 보고서야 찾았다.

## Limitations

- **정답 위치가 없다.** 기준은 SLAM 추정값이고, 사전 추정값에 따라 방향이 10~20° 달라진다.
- 작업 공간이 약 1.5 m 로 좁고 제자리 회전이 대부분이라(누적 회전 약 3,600°, 경로 약 17 m)
  위치 지표는 방향 품질을 잘 가르지 못한다.
- 전진축 동역학은 식별하지 않았다. 명령 오도메트리가 쓸모없고, 자작 ICP 는 편향이 있다.
- LiDAR 방향 90° 보정은 ICP 추정(81.5~84.2°)을 기계적 장착으로 반올림한 가정이다.
- 바이어스는 bag 마다 정지 구간에서 잰 상수다. 온도 등에 따른 변화는 반영하지 않았다.
- 조향 비교는 R² 0.69 모델 위의 시뮬레이션이다(31% 미설명). 데드밴드는 bag 이 아닌 기록값이고, 전진 · 회전 결합은 무시했다.
